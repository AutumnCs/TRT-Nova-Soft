# 常驻核心服务拆分方案

更新时间：2026-07-14

这份文档回答的是：

在当前 `小程序 + SCF + MySQL (+ Redis 可选)` 的基础上，怎样把项目从“可演示 Demo”继续推进到“可小规模稳定试运行”，并为后续更高并发留出清晰的服务化路径。

核心原则只有三条：

1. 不是一口气推翻 SCF，而是先抽“最实时、最核心、最连续”的链路
2. MySQL 继续存事实，Redis 继续存临时态
3. 先让新旧链路并行，再逐步切主

## 1. 先给结论：哪些继续留 SCF，哪些该开始抽

### 继续留在 SCF 的部分

这几类现在继续放在 SCF 是合理的：

- 登录鉴权：`auth-scf`
- 普通业务 API：用户资料、Todo、日记、植物库
- 低频后台接口
- 定时任务：`history-cleanup-scf`
- Agent 建议类能力：`agent-scf`

原因很简单：

- 这些链路对“常驻连接、毫秒级持续状态、持续吞吐”要求没那么高
- 访问模式偏低频、离散、请求式
- SCF 在这类场景下成本和维护复杂度都更合适

### 优先抽成常驻服务的部分

优先抽下面 3 块：

1. 设备最新状态服务
2. 指令下发与 ACK 跟踪服务
3. 在线状态管理服务

原因是这 3 块有共同特点：

- 高频
- 持续
- 状态变化密集
- 对延迟、吞吐、串联追踪要求高
- 后面最容易成为 SCF + MySQL 直打的瓶颈

## 2. 理想的平台链路长什么样

建议按下面的结构演进：

```text
设备
  -> OneNET / EMQX
  -> 接入入口（短期仍可由 ingest-scf 承担）
  -> 常驻 Device Runtime Service
       - 消息归一化
       - 防重 / 幂等
       - 最新状态更新
       - 在线状态更新
       - ACK / done 状态推进
       - Redis 写入
       - MySQL 事实落库

小程序
  -> auth-scf
  -> api-scf（普通业务）
  -> 常驻 Device Query / Command Service（实时设备相关）

定时任务
  -> history-cleanup-scf
```

如果用更直白的话讲：

- 设备“上报和状态推进”走常驻服务
- 小程序“查实时态、发设备命令”逐步走常驻服务
- 其余普通业务继续留在 SCF

## 3. 建议拆出来的 3 个核心服务边界

## 3.1 Device Runtime Service

这是最重要的一个。

它负责：

- 接收统一后的设备消息
- 识别 `deviceId / messageId / timestamp / type / payload`
- 做防重和幂等
- 更新 `device_latest`
- 写入 `device_history_raw`
- 推进 `device_commands` 的 `acked / done / failed`
- 更新 Redis 最新快照、在线态、命令处理中状态

它不负责：

- 用户资料
- Todo / 日记 / 植物库
- LLM / Agent

它应该是后续最先常驻化的核心。

## 3.2 Device Command Service

这个服务负责设备控制链路：

- 接收来自小程序或后端的设备命令
- 写入 `device_commands`
- 调用 OneNET / EMQX 下行接口
- 跟踪命令状态：`pending / sent / acked / done / failed`
- 提供命令查询、重试、超时补偿
- 在 Redis 标记命令处理中状态

它和 `api-scf /device/cmd` 的区别是：

- `api-scf` 更像通用业务入口
- Command Service 更像持续维护命令状态机的实时服务

## 3.3 Presence / Online State Service

这个服务可以一开始先并入 Runtime Service，后面再独立。

它负责：

- 管理设备最后上报时间
- 管理在线 / 离线状态
- 维护 Redis 在线态
- 统一输出 `online / offline / onlineStatus / lastSeenAt / offlineSinceMs`

为什么单拎出来说：

- 在线态是最典型的“高频、临时、可过期”数据
- 它天然更适合 Redis，不适合每次从 MySQL 临时拼

## 4. 为什么不是先把 `auth-scf` / `agent-scf` 一起搬走

因为收益不成正比。

当前真正会先出问题的，大概率不是：

- 登录鉴权
- 植物库
- Agent 问答

而是：

- 设备持续上报
- 最新状态读取
- 命令下发闭环
- 在线态刷新

所以正确顺序不是“全面后端重构”，而是“先把设备实时核心抽出来”。

## 5. 与现有 SCF 的并行方式

这一步非常关键。

推荐不是直接替换，而是按下面做：

### 阶段 A：接口不改，内部先并行

- 小程序入口暂时不变
- `api-scf` 仍保留 `/device/latest`、`/device/cmd`、`/device/commands`
- 但内部开始允许这些接口转发给常驻服务

这样做的好处是：

- 前端不用先大改
- 云函数和常驻服务可以并行验证
- 出问题时能快速回切

### 阶段 B：写链路先切

优先把下面两段切到常驻服务：

- 设备上报处理
- 命令下发与 ACK 跟踪

因为这两段最实时、最敏感。

### 阶段 C：读链路再切

再把这些查询切到常驻服务：

- `/device/latest`
- `/device/commands`
- `/device/command/detail`

这一步要等 Redis 最新快照和在线态已经比较稳。

### 阶段 D：SCF 降级为外围层

最终结构会变成：

- SCF：外围业务、定时任务、鉴权、Agent
- 常驻服务：设备实时核心

## 6. 推荐技术形态

如果你问“是不是要上 FastAPI”，答案是：

可以，而且对你现在这个阶段是合理的。

建议优先考虑：

- FastAPI：开发效率高，适合先把实时服务收起来
- Redis：在线态、最新快照、命令处理中状态、防重标记
- MySQL：事实数据、审计数据、历史数据、命令记录

不是因为 Python 一定比 Node 强，而是因为：

- 你现在更缺的是“清晰的常驻服务边界”
- 不是“语言层面的大换血”

如果你团队后面更偏 Go，也可以后续再换，但第一阶段没必要因为语言选择卡住服务拆分。

## 7. 迁移顺序建议

推荐顺序：

1. 保持现有 SCF 主链路可用
2. 把 Redis 实时层正式启用并观察
3. 新建常驻 Device Runtime / Command Service
4. 先接设备上报和命令状态推进
5. 再切小程序实时查询
6. 最后把 `api-scf` 里实时设备逻辑逐步减薄

一句话概括：

先把“写路径和状态机”抽出来，再抽“读路径”。

## 8. 对你这个项目最现实的阶段划分

### 当前阶段

- SCF 仍是主入口
- MySQL 是事实库
- Redis 已经是轻量实时层预备形态

### 下一阶段

- Redis 正式承接在线态、最新快照、命令处理中状态
- 常驻服务承接设备实时核心
- SCF 继续承接外围业务

### 再下一阶段

- 高并发读写主要打到常驻服务 + Redis
- MySQL 退到事实存储和审计存储
- SCF 主要做边缘业务与平台型能力

## 9. 现在不建议做的事

- 不建议一口气把所有 SCF 全改成常驻服务
- 不建议在没有真实瓶颈数据前就拆很多微服务
- 不建议把历史事实全搬进 Redis
- 不建议让 Agent 直接跨越审计链路去控制设备

## 10. 最终判断

对你这个智能植宠项目来说，比较理想的后端安排不是：

“SCF 全保留不动”

也不是：

“马上全量重写成一整套大后端”

而是：

“保留 SCF 做外围业务，把设备实时核心逐步抽成常驻服务。”

这是从 Demo 走向“小规模稳定试运行”，同时又为以后更高并发留出升级路线的最稳妥方案。
