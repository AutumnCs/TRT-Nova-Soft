# 开发规则

本文档只定义后续开发时必须遵守的原则、约束和最小自检要求，不重复描述完整架构现状。

架构现状请查看：

- [当前架构](./current-architecture.md)

## 1. 总原则

后续开发必须同时满足三件事：

1. 不破坏当前主链路
2. 不把旧逻辑重新带回
3. 不再引入低级工程问题，例如乱码、BOM、入口错位、误删页面

## 2. 页面结构规则

### 2.1 Tab 规则

底部 Tab 固定为：

1. 首页
2. 社区
3. 我的

未经确认，不允许擅自调整：

- Tab 数量
- Tab 语义
- Tab 对应页面

### 2.2 “我的花园”规则

- “我的花园”只能从“我的”页进入
- 不能独立占用 Tab
- 不能把“社区”替换成“我的花园”

### 2.3 “设备管理”规则

- “设备管理”属于“我的花园”流程
- 不应再作为“我的”页的常规独立入口

### 2.4 “开发者平台”规则

- “开发者平台”必须保留
- 不能在未确认情况下移除
- 不能和用户侧设备管理混为一页

## 3. 数据模型规则

### 3.1 `devices` 与 `device_acl` 不得混用

必须区分：

- `devices`：设备主数据
- `device_acl`：用户绑定关系与用户个性化配置

明确要求：

- `physicalCode / productId / deviceName / logicalKey` 属于 `devices`
- `alias / location / plantType` 属于 `device_acl`

### 3.2 用户侧只接触 `physicalCode`

用户前端不应直接暴露：

- `productId`
- `deviceName`
- OneNET 内部标识

### 3.3 待办规则

`todos` 必须同时绑定：

- `openid`
- `logicalKey`

禁止：

- 全表读取 todos
- 只按用户隔离，不按设备隔离

### 3.4 ACL 重复规则

同一用户对同一设备解绑再绑定时：

- 优先复活已有 `inactive` ACL
- 不允许无限新增重复 ACL

## 4. 编码与文件规则

这是必须严格执行的硬规则。

### 4.1 所有文本文件必须使用 UTF-8 无 BOM

适用文件：

- `*.js`
- `*.json`
- `*.wxml`
- `*.wxss`
- `*.md`

### 4.2 不允许再引入乱码中文

每次修改中文文案后，必须确认：

- 文件内容是正常中文
- 编译后页面显示也是正常中文

### 4.3 修改后必须做最小校验

最低要求：

1. JS 语法通过
2. JSON 可解析
3. 文件无 BOM
4. 关键中文文案肉眼可读

## 5. 代码修改规则

### 5.1 不要拿旧代码片段直接覆盖当前页面

每次改页面前，必须先判断：

1. 当前页面的职责是什么
2. 哪些逻辑已经废弃
3. 哪些入口已经迁移

否则很容易出现：

- “我的花园”重新变成“开发中”
- “设备管理”重新出现在旧入口
- “开发者平台”被误删
- 社区被误替换

### 5.2 局部问题只做局部修复

例如：

- 修花园入口，不能顺手改 Tab 结构
- 修头像显示，不能破坏首页布局
- 修设备入口，不能把“我的”页回退到旧版

### 5.3 删除文件前必须确认引用关系

删除或清理文件前，必须先确认：

- 是否仍被路由引用
- 是否仍被页面入口引用
- 是否仍被云函数或服务层引用

不能因为“看起来没用”就直接删。

## 6. 架构与移植规则

### 6.1 页面层不直接散落业务逻辑

正确调用路径应为：

- 页面 -> `services/modules/*`
- `services/modules/*` -> 适配器 / 云函数

### 6.2 云函数逐步做薄

云函数入口尽量只负责：

- 参数校验
- 权限上下文获取
- 调用纯业务规则
- 调用数据库适配

### 6.3 纯业务规则逐步脱离 `wx-server-sdk`

后续改造方向：

- 业务规则抽成纯 JS 模块
- 云函数只做 IO 和数据库操作

当前已经开始这样做的函数：

- `bindDevice`
- `updateBoundDeviceInfo`

后续建议继续处理：

- `unbindDevice`
- `getDeviceData`

## 7. 参考实现规则

`reference/onenetWebhook.example.js` 只是参考实现。

必须明确区分：

- 参考实现
- 实际部署实现

禁止把参考文件误当成线上真实代码来源。

## 8. 推荐工作流

每次改动建议按以下顺序执行：

1. 先确认页面/云函数当前职责
2. 查入口关系和调用链
3. 只改目标范围文件
4. 做最小自检
5. 再做关联页面回归检查

### 8.1 页面改动最小自检

至少检查：

- 路由还能进入
- 中文文案正常
- 无白屏
- 不影响既有 Tab
- 不影响原有入口

### 8.2 云函数改动最小自检

至少检查：

- 入参校验
- 返回结构稳定
- 不破坏既有集合字段
- 不引入重复数据

## 9. 后续开发优先级

建议优先顺序：

1. 稳定首页 `index`
2. 稳定“我的 / 我的花园 / 设备详情 / 设备设置”链路
3. 清理剩余乱码与旧逻辑残留
4. 继续把云函数业务规则抽为纯模块
5. 最后再做非主链路清理

## 10. 最重要的几条

如果只记住几条，请记住下面这些：

1. 不要改动“首页 / 社区 / 我的”这个 Tab 结构
2. “我的花园”只能从“我的”进入
3. “设备管理”属于“我的花园”流程
4. “开发者平台”必须保留
5. `devices` 管主数据，`device_acl` 管用户关系和个性化配置
6. 所有文本文件都必须是 UTF-8 无 BOM
7. 不要再拿旧代码片段直接覆盖当前页面
8. 页面层走 `services`，业务规则逐步脱离 `wx-server-sdk`
