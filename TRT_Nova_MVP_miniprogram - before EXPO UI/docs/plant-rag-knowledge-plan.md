# 植物养护 RAG 知识库规划

> 更新日期：2026-05-17

## 当前口径

当前阶段先落“轻量知识增强”，而不是一步到位做完整向量 RAG 平台。

当前优先级：

- `plant_library` 结构化植物资料
- 设备字段协议片段
- 少量业务规则片段

当前暂不优先：

- embedding
- 向量库
- rerank
- 大规模知识切块

## 1. 目标

为植物养护 Agent 提供一套可检索、可迭代、可控来源的知识库，用于回答：

- 植物品种养护知识
- 当前设备数据解释
- 设备字段协议说明
- 项目业务规则说明

目标不是做一个百科全书，而是让 Agent：

- 回答更稳
- 少胡说
- 更贴合本项目现有设备与业务场景

## 2. 知识库范围

建议分为三类知识：

### 2.1 植物养护知识

内容包括：

- 品种基本信息
- 光照需求
- 浇水策略
- 温湿度偏好
- 常见异常与处理建议

### 2.2 设备字段协议知识

内容包括：

- `soil_percent` 等字段含义
- 单位和范围
- 风险解释
- 哪些字段是硬件计算结果

### 2.3 业务规则知识

内容包括：

- 真实状态以 `device_latest` 为准
- 命令发送不等于设备执行成功
- 控制动作只能通过白名单工具触发
- 当前支持哪些能力，不支持哪些能力

## 3. 初始数据来源建议

### 3.1 项目内结构化数据

优先来源：

- `plant_library`
- `data/plants.js`

优点：

- 结构清晰
- 与当前产品内展示一致

用途：

- 作为植物基础知识主数据

### 3.2 项目文档

优先来源：

- `docs/plant-care-agent-plan.md`
- `docs/device-field-protocol.md`
- `docs/current-architecture.md`
- `docs/hardware-control-current-solution.md`
- `docs/scf-onenet-command-path.md`

用途：

- 作为字段协议和业务规则知识

### 3.3 人工整理的植物养护手册

建议后续新增：

- `docs/knowledge/plants/*.md`

例如：

- `docs/knowledge/plants/pothos.md`
- `docs/knowledge/plants/monstera.md`
- `docs/knowledge/plants/succulent.md`

内容建议：

- 品种简介
- 适合环境
- 浇水建议
- 光照建议
- 常见问题
- 与本设备指标的对应解释

## 4. 知识文档结构建议

建议每种植物用统一模板，方便后续分块与检索。

示例：

```md
# 绿萝

## 基本信息
- 类型：观叶植物
- 特点：耐阴、适合室内

## 光照
- 喜明亮散射光
- 长期暴晒可能黄叶

## 浇水
- 土壤微干再浇
- 忌长期积水

## 常见问题
### 黄叶
- 可能原因：积水、暴晒、换盆应激

### 叶片无光泽
- 可能原因：缺光、空气过干

## 与设备指标的关系
- `soil_percent < 20%`：可能偏干
- `light_val` 长期过低：可能影响长势
```

## 5. 分块策略建议

### 5.1 初期策略

初期不必一开始就上复杂向量库，可先用轻量检索策略：

- 文档按标题分段
- 每段保留：
  - 植物名
  - 主题标签
  - 正文内容

优先支持：

- 关键词检索
- 类型过滤
- 品种过滤

### 5.2 后续向量检索

当知识文档增多后，再考虑：

- 文本切块
- embedding
- 向量召回
- rerank

适合引入向量检索的时机：

- 品种文档超过几十篇
- 问题开始变复杂
- 需要更强召回质量

## 6. 检索策略建议

建议优先用“分层检索”，而不是所有文档混搜。

### 6.1 设备问题优先查协议库

适用问题：

- “soil_percent 是什么意思？”
- “run_state 是什么？”

优先检索：

- `device-field-protocol.md`

### 6.2 业务操作问题优先查规则库

适用问题：

- “为什么显示命令已发出但风扇没开？”
- “为什么 Agent 不直接改数据库状态？”

优先检索：

- 架构和控制链路文档

### 6.3 养护问题优先查植物知识库

适用问题：

- “绿萝多久浇一次水？”
- “龟背竹需要多少光照？”

优先检索：

- 植物资料文档
- `plant_library`

## 7. RAG 与规则层的分工

RAG 负责：

- 提供知识依据
- 回答植物习性问题
- 解释业务规则和字段含义

规则层负责：

- 计算当前风险
- 识别异常等级
- 生成结构化事实
- 控制执行边界

LLM 负责：

- 组织语言
- 结合检索结果和规则结果生成最终响应

这样可以避免：

- 让 LLM 直接从原始传感器值胡乱推断
- 让 RAG 替代规则判断

## 8. 推荐知识标签

每个知识片段建议带标签，便于过滤。

示例标签：

- `plant:绿萝`
- `plant:龟背竹`
- `topic:watering`
- `topic:light`
- `topic:yellow_leaf`
- `topic:device_field`
- `topic:business_rule`
- `topic:control_flow`

## 9. 回答时的引用方式

虽然前端未必要展示正式参考文献，但 Agent 内部最好保留来源元信息：

- 来源文档
- 来源片段标题
- 匹配标签

便于：

- 调试
- 质量评估
- 后续做“为什么这么建议”的解释

## 10. 第一期最小知识库建议

建议第一期先准备以下内容：

1. 植物基础知识
   - 绿萝
   - 龟背竹
   - 多肉
   - 薄荷
   - 番茄

2. 字段协议知识
   - 当前 latest / history 字段
   - 风扇控制字段

3. 业务规则知识
   - latest 才代表真实状态
   - 命令发送不等于已执行
   - Agent 控制白名单边界

## 11. 后续演进建议

### Phase 1

- 文档型知识库
- 关键词检索
- 小规模结构化植物数据

### Phase 2

- 文档增量扩充
- 统一 chunk 和标签
- 引入 embedding 检索

### Phase 3

- 结合用户历史提问优化检索
- 建立高频问题答案模板
- 做召回质量评估

## 12. 风险与注意事项

### 12.1 避免把通用养护建议说成绝对结论

植物养护知识通常是经验性建议，Agent 回答应保留一定弹性。

### 12.2 避免用知识库覆盖实时设备事实

例如：

- 知识库说“绿萝喜欢湿润”
- 但当前 latest 没显示缺水

那么回答必须优先基于实时数据，而不是仅按常识输出。

### 12.3 避免知识库和硬件协议脱节

设备字段变化后，要同步更新字段协议知识文档，否则 Agent 会解释错误。
