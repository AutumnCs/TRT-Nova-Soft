初学也不慌，一张图看懂“前端 / 后端 / 云平台”怎么配合

一、全景架构：谁在和谁说话
你的小程序跑起来，其实是下面这几块在互相通信。先记住一句话：前端管“看得见的操作”，后端管“数据的存和查”。
硬件设备 OneNet 物联网 小程序前端 腾讯云 SCF 后端 数据库
重点理解：你刚才在小程序里“绑定设备失败”，是因为前端把你输入的设备码发给后端，后端去数据库查，但查的名字对不上。我们改的是右边那个橙色“腾讯云 SCF 后端”里的查询逻辑——前端、数据库一行都没动。
二、四个角色分别是干嘛的
把下面四块当成四个“岗位”，各管一摊。

微信开发者工具

写代码 + 预览 + 上传

装在你电脑上的软件。你在这里写小程序、点“预览”看效果、点“上传”把前端代码发到微信服务器。它本身不是后端，只是前端的“编辑器+模拟器”。

微信小程序前端

pages/ · services/ · app.*

最终跑在用户手机微信里的界面和逻辑。你看到的页面、点的按钮都是前端。它自己不存数据，要“问”后端要。

腾讯云 SCF 后端

dist/scf/ 下的云函数

跑在腾讯云服务器上的程序（不是你电脑）。处理绑定、存数据、查数据。你之前部署的就是它。它叫“云函数”，按请求才运行，不用自己买服务器。

OneNet + 数据库

物联网平台 · MySQL

硬件把温湿度等数据发到 OneNet；SCF 后端把设备和用户关系存进 MySQL 数据库。两者配合，小程序才能“知道”你的设备存在。

三、“上传”和“部署”是两码事
这是新手最容易混的。一句话：上传是给“前端”用的，部署是给“后端”用的。

● 微信开发者工具里的“上传”

  • 上传的是前端代码（pages/、services/ 那些）
  • 传到微信自己的服务器，变成“开发版 / 体验版”
  • 目的是：让别人也能扫码测、或者提交审核上线
  • 本次你没改前端，所以不用上传也能用

● 腾讯云 SCF 上的“部署”

  • 部署的是后端代码（dist/scf/ 里的函数）
  • 传到腾讯云服务器，替换掉旧的后端逻辑
  • 目的是：让后端的新代码生效
  • 我们刚才做的就是这个——把改好的 api-scf 部署上去了
所以回到你的问题：这次只在“后端”动了刀，前端没碰。你在开发者工具里直接预览 / 真机调试就能测绑定，不用点上传。只有想让别人测、或正式发布，才需要上传前端。
四、你从 GitHub 克隆下来的，前端后端都有
这个仓库是一个“全家桶”：既有前端、也有后端，还混了几个历史/其他项目。下面标了颜色，绿色是当前前端、橙色是当前后端、灰色是先别看的归档。
TRT小程序/
  pages/ ← 前端：每个小页面一个文件夹
  services/ ← 前端：负责“调后端”的桥
  app.js / app.json / app.wxss ← 前端：小程序总入口
  custom-tab-bar/ ← 前端：底部导航栏
  dist/scf/ ← 后端：api-scf / ingest-scf / auth-scf / admin-scf
  admin-web/ ← 前端：网页版管理后台
  legacy/ ← 旧代码归档（别动）
  emotional_chat_fullsrc/ ← 另一个 Python 项目（别动）
  flutter_app/ ← 另一套跨端代码（别动）
  docs/ · scripts/ · reference/ ← 文档和工具脚本
结论：克隆下来的东西是前端 + 后端都有。但真正在跑的是：前端 = 根目录的 pages/ services/ app.*，后端 = dist/scf/。legacy/、emotional_chat_fullsrc/、flutter_app/ 是别的工程混进来的，初学先完全忽略它们，否则会被绕晕。
五、怎么“看代码”：从入口顺藤摸瓜
别一上来就全局搜索。按下面顺序，从“看得见的地方”摸到“背后的逻辑”。
1

看 app.json —— 知道有哪些页面

这是小程序的“目录”。里面有个 pages 数组，列出了所有页面路径，比如 pages/device/device。想看哪个功能，先在这里找名字。

2

进 pages/ 看每个页面 —— 四件套

每个页面文件夹里有 4 个文件：.wxml(长什么样) · .wxss(好不好看) · .js(点按钮干啥) · .json(页面配置)。你关心的“绑定”在 pages/device/device.js。

3

看 services/ —— 前端怎么“喊”后端

前端自己不连数据库，它通过 services/ 里的适配器（如 ScfApiAdapter）发网络请求给后端。这里就是前端和后端的“交接处”。

4

看 dist/scf/api-scf/index.js —— 后端逻辑

后端的“大脑”。里面用路由区分功能，比如 /device/bind 就是绑定设备。我们之前改的设备名兼容逻辑，就在这个文件里。

5

数据库是终点 —— 后端查的就是它

后端执行 SQL（如 SELECT * FROM devices）去 MySQL 里找记录。绑定成功，本质是“数据库里有了你和设备的关联”。

学习心法：从一个你看得见的动作出发（比如“点绑定”）→ 翻 pages/device/device.js 看它调了哪个接口 → 翻 services/ 看发给谁 → 翻 dist/scf/api-scf/index.js 看后端怎么处理 → 最后落在数据库。这样顺藤摸瓜，任何功能都能看懂。
