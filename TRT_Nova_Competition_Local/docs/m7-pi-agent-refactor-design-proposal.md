# M7：借鉴 PI Agent 语义的 NOVA Agent 重构提案

> 历史/目标文档提示（2026-09-08）：本文保留该阶段的配置、调研或实施记录，不作为当前能力与验收状态清单。旧记忆、额度、rollout 和云端结论如与后续版本不同，以当前入口为准。 当前产品见[先看这里](./先看这里.md)，技术事实见[当前架构](./current-architecture.md)。

> 状态：**Phase 0–5 已完成本地 A/B/C 自动验收候选，等待项目负责人终局人工签字；Shadow/受控灰度默认关闭**
> 范围：Agent 运行时、上下文、会话、记忆、RAG、工具编排和安全边界
> 不在本提案内：页面视觉改版、硬件控制扩权、多 Agent、后台自治任务、跨 Agent 协作

## 0. 结论先行

NOVA 不应继续让大规模正则表达式决定“用户能不能获得自然回答”，也不应把全部约束退化为一段提示词。

M7 推荐采用：

> **LLM-first 对话 + 极窄的确定性策略层 + 受控工具循环 + MySQL 会话/记忆适配器。**

其中：

- 删除当前以语义正则为主的 `in_scope / deferred / out_of_scope` 回答门控；
- 让 LLM 负责自然语言理解、陪伴语气、简单常识问答、澄清和自然的能力边界表达；
- 保留鉴权、资源归属、附件限制、工具参数校验、知识发布状态、写操作确认和高风险安全约束；
- 植物养护事实不完全交给模型自由决定是否检索，而由能力策略确保进入已发布知识检索；
- 任务工具只产出“候选任务/预览”，真正写入仍由用户确认后通过现有业务 API 完成；
- 当前生产代码复用 PI 的 agent loop、tool/event/context **设计语义**，实现 Node 20 兼容的最小内部 Runtime；它没有安装或加载官方 `pi-agent-core`，也不引入 `AgentHarness` 或整套 coding agent；
- SCF 每个请求创建短生命周期的运行实例，会话、事件和长期记忆继续以 MySQL 为事实源。

这不是“砍掉规则”，而是把规则从脆弱的自然语言分类器，收缩为不可绕过的权限与业务不变量。

## 1. 设计依据与证据边界

### 1.1 学长 PRD 与项目蓝图中的 Agent 目标

本次重构必须保留以下产品目标，而不是把 NOVA 做成通用聊天机器人：

1. NOVA 是人格化的植物养护伙伴，用户应感知到连续关系、记忆和植物背景。
2. 核心闭环是：识别/判断 → 给出建议 → 形成任务预览 → 用户确认 → 日历/执行 → 打卡或养护记录 → 后续记忆。
3. Agent 可以读取植宠事实、知识、记忆并编排安全工具，但不拥有植物事实、人格、关系和长期记忆的最终解释权。
4. Agent 不直接静默修改任务、档案或记录；业务写入必须经过明确确认和业务 API 校验。
5. RAG 只能引用已发布、经人工复核的知识；无可靠命中时必须承认不确定。
6. 会话历史、长期记忆和业务事实是三类不同数据，不能互相冒充。
7. 跨会话记忆应结构化、可查看、可编辑、可删除；模型推断的长期偏好需要用户确认。

### 1.2 当前代码的真实结构

当前 `agent-scf` 已经具备可复用的业务基础，但不是完整的 Agent runtime：

- `agent/chatHandler.js` 负责一次请求的固定编排；
- `agent/intentRouter.js` 用多组正则先决定 social、in-scope、deferred 或 out-of-scope；
- `lib/llmClient.js` 只做一次 OpenAI-compatible `/chat/completions` 调用，没有工具协议和循环；
- `rag/knowledgeSearch.js` 能查询知识，但是否查询由前置路由决定；
- `agent/petContext.js` 能组装当前植宠、事实和简单相关记忆；
- `lib/agent-store.js` 和 MySQL 表已经承载会话与结构化记忆基础；
- 任务候选由本地规则识别，返回预览，真实写入仍走业务端确认链路。

因此，当前系统更准确的定义是：

> **具有 LLM 回复节点的确定性业务工作流**，还不是能够多轮选择和执行工具的 Agent runtime。

### 1.3 当前正则门控的根因

问题不只是“某几个正则写错了”，而是同一个分类结果同时控制了多项权限：

```text
语义正则分类
  ├─ 是否调用 LLM
  ├─ 是否携带历史会话
  ├─ 是否读取长期记忆
  ├─ 是否读取植宠事实
  ├─ 是否进行 RAG
  └─ 是否生成任务候选
```

这造成了系统性故障：

- 一次误分类会同时切断回复、关系连续性、知识和工具；
- 同一句话添加问号、植物名或口语后缀，可能进入完全不同的路径；
- 为减少误放行而增加正则，会持续扩大误拒绝面；
- 测试即使全部通过，也只说明实现符合当前正则合同，不说明合同符合真实用户意图；
- 固定拒绝文案夺走了 LLM 的语气和上下文能力，产生突兀、重复和“像客服机器人”的体验。

已运行的当前回归测试为 176/176 通过；这项结果用于确认现状可复现，不能用来证明路由设计正确。

### 1.4 植友圈“小芽”的公开黑盒观察

根据用户提供的真实截图，小芽呈现出一种比 NOVA 当前实现更自然的“伙伴半径”：

- 问候：自然回应并邀请用户继续；
- “我是谁”：说明尚无身份信息，再邀请用户告诉称呼；
- `1+1`：直接回答简单常识，再轻量回到植物话题；
- 写程序、证明猜想：礼貌说明能力边界，再引导到花园/养护能力；
- 文案短、语气统一，没有暴露内部 RAG、规则或治理术语。

公开网页和项目介绍能支持的结论只有：其产品公开宣称使用“多模态智能体 + 园艺知识库”，并展示植物档案和养护能力。截图无法证明它是否使用正则、系统提示词、RAG 框架或某一种 Agent runtime。

能力边界：本项目可以研究其公开网页、公开静态资源和用户提供的黑盒行为，但不能直接控制用户手机里的微信小程序，也不能获取未公开的后端源码、系统提示词、私有 API 或数据库。除非对方开源、授权测试或提供测试环境，否则不应通过越权探测来“获取后端”。

### 1.5 对当前 DeepSeek 模型的真实只读探针

使用项目当前配置的模型和真实 API，向模型提供虚拟的只读/候选工具，只观察模型回复与 tool call，不执行应用数据库或业务写入。结果如下：

| Query | 模型行为 | 设计含义 |
|---|---|---|
| `你好` | 直接温和回复，无工具 | 简单互动不需要正则分类 |
| `我是谁？` | 选择 `get_account_nickname` | 身份可通过只读工具获取 |
| `1+1等于几` | 直接回答 2，再轻量邀请聊植物 | 可形成自然伙伴半径 |
| `编写一个简单程序` | 自然拒绝并引导到植物能力 | LLM 能承担自然边界表达 |
| `月季怎么浇水？` | 未选择知识工具，直接生成泛化建议，并出现“夏天早晚各一次”等风险表述 | 不能让模型自由决定是否检索养护知识 |
| `帮我安排一个观察任务` | 先选择读取当前植宠，而不是直接创建任务 | 需要真正的多步工具循环和确认策略 |

探针同时证明了两件事：

1. 取消语义正则拒绝门控，在互动体验上可行；
2. 仅靠提示词在养护事实、工具选择和写入权限上不可靠。

## 2. 方案比较

| 方案 | 描述 | 优点 | 关键问题 | 结论 |
|---|---|---|---|---|
| A. 全砍规则、提示词约束模型 | 所有 Query 直接交给 LLM，由 system prompt 规定边界 | 最简单、语气自然 | 提示词不是权限系统；模型会漏检索、幻觉参数、越过业务前置条件 | 不采用 |
| B. 继续完善大正则分类器 | 扩大语料和正则，追求更高拦截准确率 | 本地快、成本低 | 自然语言开放集不可能靠正则达到 100%；维护成本和误拒绝同步上升 | 不采用 |
| C. LLM-first + 窄策略层 + 工具循环 | 默认让 LLM 理解和回复，确定性层只保护权限/事实/写入 | 体验、可控性、可演进性较平衡 | 需要重构上下文、工具与评测 | **推荐** |
| D. 整套移植 PI coding agent / AgentHarness | 直接复用 PI 上层会话、扩展、技能和工具 | 表面功能丰富 | 过度引入文件/命令等能力；当前 Harness 仍有未实现接口；与 SCF/MySQL 不匹配 | 不采用 |

## 3. 目标架构

```text
微信小程序
   │
   │ user message / attachments / selected conversation
   ▼
agent-scf HTTP boundary
   ├─ 身份认证、限长、MIME、资源归属
   └─ TurnEnvelope 标准化
           │
           ▼
PlantPet Agent Runtime（每次 SCF 请求内创建）
   ├─ PI 语义兼容的最小内部 agent loop
   ├─ Persona & Response Policy
   ├─ Capability Policy
   ├─ Context Projector
   └─ Tool Registry + Tool Executor
           │
           ├──────────────┬────────────────┬──────────────────┐
           ▼              ▼                ▼                  ▼
      Session Store   Memory Store     Knowledge RAG      Domain Read Model
        MySQL           MySQL           published only    植宠/设备/记录
           │              │                │                  │
           └──────────────┴────────────────┴──────────────────┘
                                  │
                                  ▼
                       Assistant message / proposal cards
                                  │
                                  ▼
                     用户编辑与确认候选写操作
                                  │
                                  ▼
                         api-scf 业务写入与审计
```

关键点：

- SCF 无状态实例不持有长期 Agent 对象；每次请求从 MySQL 恢复投影，执行本轮，再持久化事件；
- 当前内部 Runtime 负责“模型 → tool call → tool result → 再次模型”的循环，并保留未来替换内核的 seam；它不是官方 PI Core；
- PlantPet Runtime 决定允许暴露哪些工具、每个工具读写权限、最大步数和超时；
- 业务写入不作为模型可以直接执行的能力；模型最多创建待确认的 proposal；
- `ai_messages` 是可读会话账本，`ai_conversation_events` 是追加式审计记录；二者共同形成事件支持的当前分支投影，而不是纯事件溯源。长期记忆是受控结构化事实，业务对象仍由各自表拥有。

## 4. 规则层重构

### 4.1 应删除的规则职责

以下职责不再由正则表达式承担：

- 判断普通用户 Query 是否“值得回答”；
- 根据算术、编程、问号、植物词等表面字符直接拒绝；
- 为社交问候、身份、越界问题拼装固定大段文案；
- 用一次分类结果决定是否加载历史、记忆和 RAG；
- 通过关键字直接认定用户要创建任务；
- 把“没有植物关键词”等价为“与陪伴无关”。

### 4.2 必须保留的确定性策略

| 策略 | 为什么不能只靠提示词 |
|---|---|
| JWT/openid 鉴权 | 模型不能决定调用者身份 |
| 用户/植宠/会话所有权校验 | 防止跨账户读写 |
| 消息、附件类型与大小限制 | 资源和攻击面控制 |
| 工具 JSON Schema 与业务参数校验 | 模型参数可能缺失或幻觉 |
| 工具 allowlist、每轮最大步数和超时 | 防止无限循环和越权能力 |
| 仅检索已发布知识 | 内容治理不应由模型猜测 |
| 任务/记录/档案写入前确认 | 保持用户对副作用的控制 |
| 显式否定优先，例如“不要安排任务” | 禁止误触发写入候选 |
| 高风险场景的硬边界 | 医疗、农药/毒性、设备危险动作需要稳定策略 |
| 输出来源和不确定性检查 | 防止把模型推断呈现成已知事实 |

### 4.3 能力策略不等于意图正则

能力策略解决的是“为完成这类需求，哪些可信数据或工具必须参与”，而不是“这句话准不准回答”。

推荐 v0.1 能力分类：

| 能力 | 默认上下文/工具 | 是否允许自然回复 |
|---|---|---|
| 问候、闲聊、简单常识 | 会话投影、人格策略 | 是，通常无工具 |
| 账户昵称/用户称呼 | `get_account_nickname` | 是 |
| 通用植物知识/养护方法 | `search_published_knowledge`；必要时植物实体消歧 | 是，必须基于知识结果或明确不确定 |
| 当前植宠状态 | `get_selected_plant`、设备/最新记录只读工具 | 是 |
| 历史养护与关系回忆 | 会话投影 + `recall_relevant_memories` + 养护记录 | 是 |
| 图片观察 | 视觉结果 + 可选知识检索；结构化为“可见现象/可能原因/建议下一步” | 是，不得直接确诊 |
| 创建任务意图 | 先读取当前植宠和必要事实，再 `propose_care_task` | 是，只返回预览 |
| 重型非植物工作 | LLM 自然说明能力边界并引导 | 是，不暴露生产型工具 |

能力选择可以由模型结构化输出完成，也可由一个小型分类模型或有限的确定性业务信号辅助；无论选择器怎么实现，都不得再切断基础会话历史，也不得替代工具侧权限校验。

## 5. PI 的复用边界

### 5.1 可复用

基于 2026-09-01 对 PI 官方仓库当前主分支的源码审计，可考虑复用：

- 低层 `Agent` 状态与生命周期；
- `runAgentLoop` / `runAgentLoopContinue`；
- 工具定义、JSON Schema 校验和 tool result 回灌；
- 模型消息流、tool execution 事件和订阅；
- `transformContext` 与 `convertToLlm` 的分层接口；
- steering/follow-up 等队列思想；
- abort、idle 和最大循环控制思想。

### 5.2 暂不复用

- 当前 `AgentHarness`：官方源码中 `prompt`、`compact`、`resume`、tree navigation 等多项能力仍返回 `HarnessNotImplemented`；
- 整套 `pi-coding-agent`：其文件系统、shell、编辑器、技能和 coding session 语义超出植宠产品需求；
- PI 的 JSONL/SQLite 会话实现：本项目已有 MySQL、SCF 和业务数据模型，应编写适配器而不是双重事实源；
- coding agent 的自动压缩、分支和扩展机制：可借鉴设计，但不能不经评审直接移植。

### 5.3 运行环境风险

当前 PI core 包是 ESM，声明 Node `>=22.19.0`；当前 `agent-scf` 是 CommonJS 且没有在自身 `package.json` 固定 SCF Node 引擎。因此“安装依赖即可上线”尚未成立。

首个 PoC 必须先验证：

1. 腾讯云 SCF 实际可选的 Node 运行时；
2. CommonJS handler 与 ESM core 的加载/打包方式；
3. 部署包体积、冷启动、网络超时和内存；
4. DeepSeek tool calling 与 PI 消息转换的兼容性；
5. 并行工具、重试和重复提交的幂等语义。

如果部署环境不能满足 PI core 的 Node 版本，备选方案不是强行引入完整 PI，而是先按相同接口实现一个最小内部 loop seam，等运行时升级后再替换内核。

## 6. PlantPet Runtime 的模块设计

Phase 2–5 已落地的代码边界如下；这是 PI 语义兼容的最小内部实现，不是官方 PI Core 的源码副本：

```text
dist/scf/agent-scf/runtime/
  plantPetRuntime.js            # 一轮运行入口、循环上限、事件收集
  turnEnvelope.js               # 标准化输入，不包含业务判断
  capabilityPolicy.js           # 决定必须/允许暴露的能力与工具
  contextProjector.js           # 从各数据源生成本轮模型视图
  toolRegistry.js               # 工具元数据、allowlist、owner 绑定和 proposal 草稿
  sessionAdapter.js             # MySQL 消息账本 + 审计事件的有效分支投影
  memoryAdapter.js              # 已确认 user_preference 的相关召回
  modelAdapter.js               # DeepSeek 与 PI 消息/工具协议适配
  shadowRuntime.js              # 默认关闭的脱敏影子对比
  rolloutRuntime.js             # 稳定抽样、结果门禁、回落与原子保存
```

proposal 持久化、分支、撤回、`clientTurnKey` 和消息保留由 `lib/agent-store.js` 负责；正式记忆/任务确认由 `api-scf` 的独立业务 API 负责。`chatHandler.js` 目前仍承载 legacy 回落链路，因此“退化为纯 HTTP/application controller”尚未完成，不能把模块已拆出描述成 legacy 已删除。

## 7. 工具目录与权限模型

### 7.1 v0.1 当前已实现并允许暴露给 Agent loop 的工具

| 工具 | 类型 | 输入要点 | 输出要点 | 副作用 |
|---|---|---|---|---|
| `get_account_nickname` | 只读 | 当前鉴权用户，不接受任意 openid | 昵称与是否默认昵称 | 无 |
| `get_selected_plant` | 只读 | 会话中选中植宠 ID | 植宠档案、品种和只读摘要 | 无 |
| `search_published_knowledge` | 只读 | 查询、实体、类别 | 已发布片段、来源、更新时间 | 无 |
| `recall_relevant_memories` | 只读 | 当前用户、Query、可选植宠 | 相关结构化记忆 | 无 |
| `propose_memory_candidate` | 候选 | 明确表达的非敏感称呼偏好 | 待确认 memory proposal | 只写候选区，不写长期记忆 |
| `propose_care_task` | 候选 | 当前植宠、动作、时间、依据 | 可编辑任务预览和 proposal ID | 只写候选区，不写任务表 |

`get_recent_care_events` 和 `get_recent_device_facts` 仍属于后续候选能力，当前没有登记到模型工具表，也不能按已实现能力汇报。

### 7.2 v0.1 不提供给模型的工具

- 任意 SQL；
- 任意 openid 或跨账户资源读取；
- 直接创建/修改/删除正式任务；
- 直接修改植物档案和养护记录；
- 直接控制硬件；
- 文件系统、shell、网页浏览和代码执行；
- 后台定时运行、自主重试到成功；
- 多 Agent 派生、handoff 或跨会话自动发消息。

### 7.3 确认链路

```text
用户自然语言明确提出任务
  → Agent 获取当前植宠/必要事实
  → propose_care_task 返回候选
  → 前端显示“预览并编辑”
  → 用户修改或确认
  → api-scf 重新验证 owner、字段、幂等键
  → 以 proposal key 幂等写入正式任务
```

任何提示词注入都不能绕过这条链路，因为 Agent loop 根本不持有正式写入工具。

## 8. 上下文、会话、记忆和 RAG

### 8.1 四类信息必须分开

| 层 | 是什么 | 事实源 | 生命周期 |
|---|---|---|---|
| 会话 | 用户/助手/tool 的有序交互事件 | MySQL session/event 表 | 按会话保留，支持多会话和分支语义 |
| 长期记忆 | 称呼偏好、已确认偏好、可复用关系事实 | MySQL memory 表 | 跨会话，可查看/编辑/删除 |
| 业务事实 | 植宠、设备、任务、养护记录 | 现有业务表 | 由业务服务维护 |
| 知识 | 已发布养护文章和图鉴 | 知识库 | 有来源和版本 |

### 8.2 Context Projector

每轮不应把所有数据拼成一大段文本。建议生成结构化视图：

```text
System policy
  ├─ NOVA 人格与表达边界
  ├─ 证据和不确定性规则
  └─ 工具使用规则

Conversation projection
  ├─ 当前分支最近消息
  ├─ 编辑/撤回后的有效事件
  └─ 必要的历史摘要

Private context（只有需要时）
  ├─ 当前账户称呼
  ├─ 当前植宠与事实
  ├─ 相关养护事件
  └─ 相关长期记忆

Knowledge context
  ├─ 已发布片段
  ├─ 来源、更新时间
  └─ no-match 状态
```

一次能力判断错误不再让整段会话历史消失；工具只补充本轮确实需要的私有事实。

### 8.3 记忆策略

现有 MySQL 结构化记忆可继续演进，不建议现在引入知识图谱：

- 账户昵称直接读取用户资料，不需要复制为“AI 记忆”；
- 确定性的业务事件可由业务系统形成记忆事件；
- 模型推断的称呼、偏好、关系信息先成为 memory candidate，用户确认后才长期保存；
- 召回从单纯字符 n-gram 升级为“类型过滤 + 实体/时间/植宠约束 + 语义相关度”的混合检索；
- 记忆条目保留来源事件、创建原因、置信度、更新时间和删除状态；
- 会话摘要只能帮助压缩上下文，不能自动获得长期事实地位。

知识图谱只有在出现大量稳定实体关系、跨植宠/设备/家庭成员推理且普通结构化查询无法支撑时才值得引入。目前它会增加数据治理和一致性成本，不能解决正则误拒绝、工具权限或会话断裂这些根因。

### 8.4 RAG 策略

- 通用植物养护问题默认触发已发布知识检索；
- 当前植宠状态问题同时读取业务事实和相关知识；
- 无命中时明确说“当前知识库没有足够依据”，模型可以给低风险观察建议，但不能伪造来源；
- 检索结果必须保留文章 ID、标题、来源、更新时间和片段；
- 模型回答后做引用完整性检查；
- 植物实体不确定时先澄清，不用相似名称强行匹配；
- RAG 内容是非可信输入，不能覆盖系统策略或发起工具调用。

## 9. 典型一轮运行流程

### 9.1 简单互动：`1+1等于几`

```text
鉴权与输入校验
  → 加载当前会话投影
  → LLM 直接回答“2”并保持 NOVA 语气
  → 不调用植宠、知识或任务工具
  → 保存消息事件
```

### 9.2 身份问题：`我是谁？`

```text
LLM 选择 get_account_nickname
  → 工具从当前鉴权用户资料读取昵称
  → LLM 说明这是账户称呼而非真实身份
  → 附带隐私提醒，不要求敏感信息
```

### 9.3 养护知识：`月季怎么浇水？`

```text
能力策略认定为植物养护事实问题
  → 必须执行 search_published_knowledge
  → 若命中，基于品种/季节/盆土等条件回答并显示来源
  → 若不足，先询问环境或说明不确定
  → 不生成“一天几次”式无条件结论
```

### 9.4 任务：`帮我安排一个观察任务`

```text
读取选中植宠
  → 若没有选中，询问作用对象
  → 读取必要事实
  → propose_care_task 生成候选
  → 前端预览并编辑
  → 用户确认后由 api-scf 正式创建
```

### 9.5 非领域重型请求：`证明哥德巴赫猜想`

```text
LLM 直接说明这不属于 NOVA 能可靠完成的任务
  → 简短引导回植物/花园能力
  → 不暴露内部“规则层拦截”或固定治理模板
  → 不影响后续会话和已确认称呼记忆
```

## 10. 迁移计划与验收闸门

### Phase 0：冻结基线与双轨评测

- 冻结当前 176 条路由/记忆测试作为 legacy 行为记录；
- 新增产品级评测集，不把 legacy 预期直接当作新架构真理；
- 采集当前 false reject、任务误触发、RAG 命中和延迟基线；
- 不改变线上行为。

**出口条件：** 新旧行为差异清单可读，已标出哪些旧测试应保留、重写或废弃。

### Phase 1：PI 兼容性 Spike

- 在独立目录验证 ESM/Node/SCF 打包；
- 接一个假的模型和 2 个纯只读假工具；
- 验证多步 loop、tool schema、abort、超时、事件顺序；
- 不接真实业务库，不改变现有 chatHandler。

**出口条件：** 提供真实命令、退出码、部署包体积、冷启动/执行时间和失败证据。若 SCF 运行时不兼容，明确选择内部 loop seam 或升级运行时。

#### 2026-09-03 实测结果

- M7 新建 42 条产品级场景：legacy 中 13 条绕过模型、12 条进入无历史/无私有上下文的受限 LLM，只有 17 条进入完整 LLM 路径；
- legacy M6 路由/记忆回归 176/176 通过，新产品合同结构校验 5/5 通过；
- 隔离 PI Core Spike 在 Node 24.16、22.19 和 20.19 上均为 6/6 通过；
- Node 22.19 单次冷导入样本约 330 ms，Node 20.19 约 465 ms；这些是 Windows 本地样本，不是 SCF P95；
- 依赖安装树为 58.49 MiB，独立 Spike zip 为 14.70 MiB；完整 `agent-scf` 生产合包尚未构建；
- 腾讯云官方当前标准 Node.js 运行时最高为 20.19，而 PI Core 声明 `node >=22.19.0`；Node 20 的测试通过不消除上游支持边界；
- 因此暂不直接把 PI Core 加入生产 `agent-scf`，等待在标准 SCF 内部兼容 runtime 与 Node 22 Custom Runtime 两条路线之间确认。

完整命令、退出码和限制见 `spikes/m7-pi-agent-core/RESULTS.md`。

### Phase 2：只读 Shadow Runtime

- 接入 `get_account_nickname`、`get_selected_plant`、`search_published_knowledge`；
- 对同一测试 Query 并行生成新架构决策，但不向用户展示、不执行写操作；
- 记录 legacy route 与新 tool trace 的差异。

**出口条件：** 跨账户读取为 0，知识问题检索召回达标，未发生副作用。

#### 2026-09-03 路线确认与实测结果

- 用户确认路线 A：标准 SCF Node 20 + PI 语义兼容的最小 `PlantPetRuntime`；不采用标准 Node 20 强行加载官方 PI Core，也不在参赛版新增 Node 22 Custom Runtime/镜像；
- 新 runtime 通过默认关闭的 `AGENT_SHADOW_ENABLED` 接到 `chatHandler` 外层，HTTP 返回仍是 legacy response；
- 三个工具均只读，账号和选中植宠范围由后端注入，模型 schema 不接受 openid 或任意 PlantPet ID；
- 植物知识每轮策略预检，明确身份问法由窄能力策略补充账号昵称；这些策略不决定 Query 是否可回答；
- thinking 模式 `reasoning_content` 回灌、策略预检与模型 tool call 消息语义均已由真实 provider 探针验证；
- 最终五场景真实 provider 探针为 5/5 完成、0 缺失预期工具、0 非必要私有工具、0 工具失败、0 业务写入；
- Shadow 专项 12/12，Shadow + 相关 legacy/RAG/身份聚焦回归 188/188，仓库全量回归 332/332。完整证据与限制见 `docs/m7-phase2-shadow-runtime-results.md`。

### Phase 3：受控灰度对话

- 简单互动、身份、通用植物知识走新 runtime；
- 任务仅返回候选，不写正式任务；
- 增加 provider failure、timeout、tool error 的降级文案；
- 保留可切回 legacy 的 feature flag。

**出口条件：** false reject 显著下降，RAG 来源完整，P95 延迟和成本在接受线内。

#### 2026-09-03 本地实现与受控验证

- 用户已授权进入 Phase 3；实现采用 ADR 0003 的“稳定会话抽样 + 能力所有权 + 结果完整性”三重门禁；
- 普通互动、明确账号称呼、轻量常识和通用植物知识可以由新 runtime 接管；任务、记忆、附件、当前植宠状态、高风险和安全请求继续由 legacy 负责；
- 42 场景真实 provider 探针选中 19、接管 18、安全回落 1；16 个 legacy 误拒候选中 15 个被接管，10 个答案级语义断言全部通过，缺失工具、非必要私有读取、失败工具和业务写入均为 0；
- 本地直连 provider P50 1948 ms、P95 6519 ms、总 token 25838；这些不是腾讯云 SCF P95；
- 真实 `/auth/login -> /agent/chat -> MySQL` 本地链路证明算术与身份由新 runtime 接管、明确任务仍回落 legacy；未重建本地数据库；
- 灰度总开关默认关闭，尚未部署到体验版/正式版。完整结果、能力表、回滚方式和限制见 `docs/m7-phase3-controlled-rollout-results.md`。

### Phase 4：会话/记忆整合

- 引入事件式会话投影；
- 编辑/撤回后的上下文只投影有效分支；
- 记忆候选、确认、查看、修改、删除形成闭环；
- 业务事实仍不复制成自由文本真相。

**出口条件：** 同账户跨会话称呼和已确认偏好可召回；删除后不可再召回；不同账户严格隔离。

#### 2026-09-03 当前实现状态（待终局验收）

- `ai_messages` 继续作为可读会话账本，新增 `ai_conversation_events` 记录 `turn_committed`、`conversation_forked`、`exchange_withdrawn` 等审计事件；`sessionAdapter`/`contextProjector` 只向模型投影当前有效分支和未撤回完整轮次。这是**事件支持的投影**，不是纯 event sourcing。
- 重新编辑在目标用户消息之前事务性创建新会话，按时间顺序复制最多最近 40 条前缀消息及媒体引用，原会话不被覆盖；撤回只允许本人会话的最后一组 user/assistant，撤回时取消该轮未确认 proposal、删除该轮会话媒体并写审计事件。
- 文本 Chat、Vision、文档分析和受控 Runtime 轮次都可携带 `clientTurnKey`；同一 key 的网络重试复用已提交 exchange，跨会话复用冲突，被撤回或被保留策略清理的 key 保留为不可重放 tombstone。
- 20 轮（40 条消息）/30 天裁剪在原子 exchange 保存内执行：裁剪前解除 proposal 的源消息引用并使 `pending` proposal 过期，清理消息媒体，把事件 payload 脱敏为只含清理原因的 tombstone，同时保留 event key 防止旧回复复活。
- 长期记忆仅召回相关、已确认的 `user_preference`；用户明确表达称呼偏好时先形成 `memory_preference` 的 `pending` proposal，只有 `/ai/memory-proposal-confirm` 成功后才写 `ai_memories.user_confirmed=1`。用户可取消候选，敏感信息在工具参数和 API 确认两侧拦截；档案、任务、日记、诊断等业务事实不复制成自由文本长期记忆。
- 助手页面对会话加载、文本、图片和文档发送使用 `PlantPet + session + epoch` 异步 scope guard；切换植宠/会话或卸载页面后，旧响应不得覆盖当前 UI。
- 上述代码和专项测试已存在；本节不填写尚未跑完的终局全量/API/开发者工具验收数字，也不把它标成体验版或真机已验证。

### Phase 5：任务候选闭环

- 接 `propose_care_task`；
- 前端预览/编辑/确认；
- api-scf 做最终 owner、字段和幂等校验；
- 明确否定句不得产生候选。

**出口条件：** 正式写入确认绕过率为 0，重复提交不产生重复任务。

#### 2026-09-03 当前实现状态（待终局验收）

- 受控 Runtime 的每轮 allowlist 只有在 `classifyTaskIntent(...).state === 'request'` 时才同时开放 `get_selected_plant` 和 `propose_care_task`；普通建议、模糊任务词和明确否定均不得产生 care-task proposal。proposal 工具只形成草稿，原子保存后状态为 `pending`，不直接写 `todos`。
- Vision 沿用同一严格意图判定，并额外要求：当前 PlantPet 存在、分析确定为植物、至少一个置信度不低于 0.7 的候选名称与当前 PlantPet 昵称/品种匹配且存在建议动作。普通图片建议保持零任务；满足全部条件时才在图片 exchange 内保存 `pending` proposal。
- 助手消息卡只对有效 `pending` proposal 提供“预览并编辑”；任务表单从后端按 proposal key 重新读取，锁定 PlantPet 归属但允许用户修改任务字段，用户可确认或取消。
- `/care/task-proposal-confirm` 在事务内重新验证 JWT owner、proposal 类型/状态/过期、PlantPet owner 和任务字段；`care_task_creation_keys(openid, proposal_key)` 让重复确认返回同一正式任务。普通 `/care/task-create` 不接受伪装为 AI 来源的绕过写入。
- 当前代码未给模型设备控制、任意 SQL、直接任务写入、后台重试、多 Agent 或跨会话自动执行权限；正式副作用仍停在用户确认后的 `api-scf`。
- 上述代码和专项测试已存在；终局验收数字、目标云 SCF 性能、体验版与实体手机结论待后续验收后另行填写。

## 11. M7 Agent 验收矩阵

### 11.1 对话半径与误拒绝

- `你好`、`你好？`、`你好!` 行为一致且自然；
- `我是谁` 能读取账户称呼，并说明隐私边界；
- `你可以叫我 dola` 产生可确认的偏好候选；
- 确认后，新会话中 `我是谁` 能记得称呼；
- `1+1等于几`、`1+2是多少个月季`、`1+2是多少朵玫瑰花` 不被正则硬拒绝；
- 写程序、证明猜想等重型请求自然收束，不出现固定大段模板；
- 任意标点、空格、大小写和口语后缀不会改变权限边界。

### 11.2 知识与 RAG

- `月季是什么` 能正常介绍，并提供已发布来源；
- `月季怎么浇水` 必须检索知识，不给无条件频率；
- 无知识命中时不伪造来源；
- 当前植宠与问题植物不一致时先澄清，不借用错误档案；
- 知识片段中的提示词注入不能改变系统策略或发起工具。

### 11.3 记忆与会话

- 同一植宠可以有多个会话；
- 新会话能召回已确认长期偏好，不把所有旧对话原文都塞进上下文；
- 编辑消息后，后续上下文基于新分支；
- 撤回/删除后，被撤回内容不再影响投影；
- 记忆删除后，新会话不可召回；
- 账户昵称、业务事实、长期记忆来源可区分；
- A 用户的会话、植宠、记忆永远不出现在 B 用户上下文。

### 11.4 工具与任务

- 模糊的“观察一下”不会自动创建任务；
- `不要安排任务，只告诉我怎么做` 不产生候选；
- 明确创建任务时先确认植宠对象和必要字段；
- 工具参数缺失、枚举错误、伪造资源 ID 被执行器拒绝；
- 模型重复 tool call 不产生重复副作用；
- 未确认 proposal 永远不进入正式任务表；
- 当前版本不存在硬件写工具、任意数据库工具和跨账户工具。

### 11.5 图片与附件

- 图片和文本一起发送、保存、切页后恢复；
- 图片只产生“可见现象”，不冒充确诊；
- 与当前植宠无关的图片不会自动为当前植宠创建任务；
- 文档内容按非可信上下文处理，不能覆盖工具策略；
- provider 无结构化视觉结果时显示可恢复失败，不丢原附件。

### 11.6 故障与性能

- 模型超时、429、5xx、非法 tool args、tool timeout 均有可恢复路径；
- 回答被 token length 截断时不展示半句高风险建议；
- 每轮记录 model、tool、耗时、错误类别和 proposal 状态，不记录密钥；
- 统计 P50/P95 总延迟、模型轮数、工具次数、token 和 RAG 命中率；
- PI 引入前后分别记录部署包体积和冷启动。

建议核心指标：

| 指标 | 目标性质 |
|---|---|
| 普通 Query 误拒绝率 | 显著低于 legacy，接近 0 |
| 未授权数据访问率 | 必须为 0 |
| 写入确认绕过率 | 必须为 0 |
| 植物事实问题知识检索召回率 | 设高门槛并人工抽检 |
| 无来源事实伪装率 | 必须为 0 |
| 任务意图 precision / recall | 分别统计，不能只看总准确率 |
| 跨会话确认记忆召回率 | 高且可删除 |
| P50 / P95 延迟与成本 | 以 Phase 0 基线和比赛演示体验设闸门 |

## 12. 本提案明确不做的事

为避免“重构 Agent”被扩大成未经确认的自治平台，本轮不默认加入：

- 多 Agent、子 Agent 或 Agent handoff；
- Agent 自己创建长期后台任务；
- durable execution、任意 checkpoint 恢复或跨请求常驻进程；
- coding-agent 的 shell、文件编辑、网页访问和 skill 系统；
- Agent 直接控制硬件；
- Agent 自动修改植物档案、正式任务和养护记录；
- 用知识图谱替换现有 MySQL 事实模型；
- 将全部原始对话无期限写入长期记忆；
- 将 PI 的 Harness 现状描述成已完整可用的生产运行时。

## 13. 进入 PoC 前需要确认的架构决策

1. **同意删除语义正则回答门控**，只保留确定性的权限、安全和业务不变量。
2. **同意采用 PI 低层 Agent Core 的兼容性 Spike**，不采用当前 AgentHarness 和整套 coding agent。
3. **同意 MySQL 继续作为会话、记忆和业务事实的唯一事实源**，PI 只负责单轮运行和工具循环。
4. **同意植物养护事实默认强制检索已发布知识**，而不是完全由模型自由选择是否 RAG。
5. **同意 v0.1 的模型工具只读或只生成 proposal**，正式写入继续由用户确认后的 api-scf 完成。
6. **同意暂不引入知识图谱、多 Agent、后台自治、硬件写入和 coding 工具**。
7. **已确认 SCF Node 运行时路线**：参赛 v0.1 保留标准 SCF，并实现 PI 语义兼容的最小 PlantPet runtime；不采用未经支持的标准 Node 20 + 官方 PI Core，Node 22 Custom Runtime/镜像留待后续平台化评审。

Phase 0 基线、Phase 1 隔离 PoC、Phase 2 只读 Shadow Runtime、Phase 3 本地受控灰度、Phase 4 会话/确认式记忆和 Phase 5 任务 proposal 均已完成本地代码与 A/B/C 自动关闭门。2026-09-03 的 Run16 为 403/403 单元、5/5 产品合同、42/42 legacy 基线、148/148 本地 MySQL/API/已配置 Provider、88/88 DevTools、31 张截图、0 页面运行时异常，总退出码 0；当前只可称为“本地自动验收候选通过，等待项目负责人终局人工签字”。Shadow 与受控灰度总开关仍默认关闭；没有部署到体验版/正式版，没有官方 PI Core 生产接入、目标云 SCF 多样本 P50/P95、实体手机或真实用户灰度结论。

迁移到云端时必须保留 owner/确认/幂等、有效分支、撤回与保留策略 tombstone、proposal 生命周期和前端 async scope 等业务不变量，同时替换本地身份、MySQL 实例、BLOB 媒体与文件凭证。具体步骤见 [`local-to-cloud-deployment-guide.md`](./local-to-cloud-deployment-guide.md)；`deployment/cloud-initial/` 是初始审查候选，不是已部署版本。
