# 系统隐患与稳定性说明

> **归档说明（2026-07-19）**：本文记录特定版本的首页轮询和 latest 回显风险；有效问题已合并到当前现状与 R3 实施步骤，不再单独维护。

## 1. 当前链路概览

当前设备控制与状态回显的主链路是：

1. 小程序首页调用 `api-scf /device/cmd`
2. `api-scf` 调 OneNET 物模型下发属性
3. 设备通过 MQTT 收到 `thing/property/set`
4. 设备执行开关动作，并回 `thing/property/set_reply`
5. 设备再通过 `thing/property/post` 上报当前真实属性
6. `ingest-scf` 接收 OneNET 推送并写入 `device_latest` / `device_history_raw`
7. 小程序首页通过 `api-scf /device/latest` 从 `device_latest` 回显状态

这条链路里，控制成功和状态显示正确是两件事：

- 控制成功：命令是否真正发到设备并执行
- 状态正确：设备执行后的真实状态是否被上报并入库，再被前端读回

## 2. 已确认的问题点

### 2.1 首页轮询曾被重复定义覆盖

首页文件 `pages/index/index.js` 里曾存在两套同名的：

- `startAutoRefresh()`
- `stopAutoRefresh()`

后定义的 `5 秒轮询` 会覆盖前面的 `60 秒轮询`，导致首页实际仍然是高频调用 `/device/latest`。

这会放大以下问题：

- SCF 超时
- MySQL 压力增大
- 网络抖动时更容易出现“设备加载失败”
- 日志和 CLS 量明显上升

当前已修正为仅保留首页 `60 秒` 低频状态轮询，并且只刷新设备状态，不联动刷新 todo。

### 2.2 `ingest-scf` 对 bool 属性的入库解析存在兼容问题

之前 `ingest-scf` 处理上报参数时默认按对象读取：

```js
const value = item?.value;
```

这会导致设备如果直接上报：

```json
{
  "params": {
    "test": true
  }
}
```

则 `value` 会被读成 `undefined`，从而影响 `device_latest.params_json` 的正确写入。

当前已修正为同时兼容两种格式：

- `test: true`
- `test: { value: true, time: ... }`

### 2.3 首页风扇状态显示依赖数据库 latest 快照

首页风扇卡片并不是直接读取 OneNET，而是读取：

- `api-scf /device/latest`
- MySQL `device_latest.params_json`

因此，只要 `device_latest` 没有最新风扇状态，或者前端没正确解析，页面就会表现为：

- 暂无上报
- 状态闪一下又回去
- 与 OneNET 页面显示不一致

### 2.4 首页请求失败时缺少“保留上次成功数据”的降级策略

当前首页一旦 `loadDevices()` 失败，容易直接把设备显示重置为默认态。

风险是：

- 用户看到“设备加载失败”
- 但其实只是一次网络抖动
- 页面体验会比实际故障程度更差

更稳妥的策略应该是：

- 请求失败时保留上次成功数据
- 页面只提示“刷新失败，当前展示为上次数据”

## 3. 高频调用的主要隐患

### 3.1 SCF 调用次数增长

如果首页持续高频轮询，会直接增加：

- `api-scf` 调用次数
- 腾讯云日志量
- 网络失败暴露频率

### 3.2 MySQL 压力增大

`/device/latest` 会涉及：

- ACL 查询
- `device_latest` 查询
- `devices` 查询

当用户数和设备数上来后，高频调用会首先打在数据库上。

### 3.3 异常放大

原本偶发的：

- `ERR_CONNECTION_CLOSED`
- `ERR_EMPTY_RESPONSE`
- `request:fail timeout`

在高频轮询下会被感知成“系统经常不稳定”。

## 4. 推荐的首页刷新策略

首页只调整首页自己的行为，不影响其他页面模块：

### 4.1 设备状态

推荐刷新时机：

1. 进入首页时拉一次
2. 用户手动点击“刷新状态”
3. 风扇命令成功后延迟拉一次
4. 可选低频静默轮询：`60 秒`

不建议：

- `5 秒` 高频轮询
- 每次刷新设备状态时联动刷新 todo

### 4.2 todo

推荐刷新时机：

1. 首次进入页面
2. 切换设备
3. 新增待办后
4. 完成待办后
5. 修改待办紧急状态后

不建议和设备状态绑定轮询。

### 4.3 天气

天气适合低频刷新或进入页面刷新，不需要跟设备状态同步频率一致。

## 5. 设备离线提醒是否有滞后

有，而且这是当前逻辑下的正常现象。

当前离线提醒的判断来自 `services/modules/AlertService.js`：

- `OFFLINE_THRESHOLD_MS = 10 * 60 * 1000`

这意味着设备超过 `10 分钟` 没有新上报，才会被判断为离线。

再叠加首页刷新节奏后，离线提醒的总滞后通常来自三段：

1. 设备真实停止上报
2. 等待超过 `10 分钟` 离线阈值
3. 等待下一次首页刷新 / 手动刷新

所以当前离线提醒不是“实时断线秒级提醒”，而是“基于最新上报时间的延迟判断”。

### 5.1 当前方案的优点

- 不容易误报
- 对偶发网络抖动更宽容
- 对 MVP 阶段更稳

### 5.2 当前方案的代价

- 离线提醒有明显滞后
- 设备刚断开时，首页短时间内仍可能显示在线

### 5.3 后续建议

如果后面需要更敏感的离线提醒，可考虑：

1. 将阈值从 `10 分钟` 调整到 `3~5 分钟`
2. 在设备侧增加更稳定的心跳上报
3. 让后端基于推送时间做离线状态计算，而不是完全依赖首页触发

## 6. 多设备场景下的建议

### 6.1 latest 表继续作为读模型

首页只读：

- `device_acl`
- `device_latest`

不要在首页请求里混入过多历史计算。

### 6.2 控制与状态严格分离

- `/device/cmd` 只代表命令发出
- `device_latest` 才代表设备真实状态

### 6.3 首页失败要降级，不要直接清空

多设备时，接口偶发失败更常见。

建议首页：

- 保留上次成功数据
- 单独标记“本次刷新失败”
- 不要直接把设备列表和状态都打回默认值

## 7. 当前最建议优先落地的事项

1. 保持首页只做低频设备状态轮询
2. 保持 todo 按事件刷新，不跟设备状态轮询绑定
3. 确保 `ingest-scf` 已部署最新版本，正确写入 bool 属性
4. 检查 `device_latest.params_json` 是否已稳定包含风扇最新状态
5. 首页后续补充“失败保留上次数据”的降级逻辑

## 8. 一句话结论

当前最大的稳定性隐患不是物模型本身，而是：

- 首页刷新策略过重
- `ingest-scf` 对状态回写的兼容性曾存在缺口
- 首页显示对数据库 latest 快照过于敏感，且缺少失败降级

把这三点收稳之后，多设备和较高调用频率下的可用性会明显提升。
