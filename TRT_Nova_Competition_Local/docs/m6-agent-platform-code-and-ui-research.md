## 2. 手机消息操作的共同模式

### 2.1 默认态

三款产品的手机默认态有稳定共同点：

- 对话正文是主视觉，消息旁不常驻编辑、撤回等操作栏；
- 输入框悬浮在历史之上，操作入口不会为每条消息增加固定高度；
- 用户无需在阅读每条消息时持续看见低频管理功能；
- 复制、编辑、删除等能力的权限与呈现位置分离。

因此，“只把文字按钮换成三个常驻图标”仍然不是手机端正确解法。它虽然比实体按钮轻，但会在每条用户消息下重复占据视觉空间，并且容易错位。

### 2.2 长按态

三款产品都使用临时上下文层，但视觉细节不同：

- ChatGPT 和 DeepSeek 在长按后显示带图标和文字的浮层菜单；
- 腾讯元宝同样把低频操作放进长按后的临时菜单；
- 菜单覆盖在内容之上，不重新排版整个消息列表；
- 操作完成或点击其他区域后退出该状态。

这说明本项目应学习的是“默认隐藏、上下文触发、临时覆盖、能力门禁”四个结构原则，不是复制某一家产品的配色、圆角或完整菜单项。

## 3. NOVA 的适配结果

### 3.1 视觉与交互

当前 `pages/assistant` 的最终方案是：

- 默认消息流完全不渲染复制、编辑、撤回控件；
- 只有长按本人用户消息才打开临时菜单；
- 菜单显示图标和文字，不要求用户猜测单个抽象图标；
- 菜单锚定长按位置并做左右边界限制，靠近底部时向上翻转；
- 点空白、滚动消息、切换/隐藏页面、开始发送或执行动作都会关闭；
- 菜单是固定覆盖层，不改变气泡尺寸和消息列表布局；
- 仍沿用 NOVA 的纸张底色、黑色边框与蓝色投影，没有引入另一套视觉系统。

菜单只针对用户自己的后端消息。助手回答、加载占位、本地未发送草稿和错误卡不会获得重新编辑或撤回权限。纯文字消息以及能够从本人私有媒体记录恢复原件的图片/文档消息可以重新编辑；旧版缺少永久媒体标识的附件消息不展示虚假入口。

### 3.2 能力与数据流

交互变化没有重写会话模型：

```text
后端 message
  -> decorateMessageActions(message, context)
  -> canCopy / canRewrite / canWithdraw
  -> 用户长按
  -> buildMessageActionMenu(message, point, viewport)
  -> 临时菜单
  -> 既有 copy / rewrite / withdraw 流程
```

- **复制**：复制当前用户消息文本；E2E 受控截获并核对负载，不污染验收机器剪贴板。
- **重新编辑**：对用户纯文字消息以及已保存原件的图片/文档消息开放；附件消息先把原文字和原附件恢复到 composer。提交后复制目标消息之前的前缀到新会话，再发送修改后的文字与附件，原会话不改写。
- **撤回本轮**：只对当前会话最后一个用户—助手消息对开放，并保留二次确认；后端继续校验 JWT openid、会话所有权和最后一轮条件。

所以本轮只替换呈现/触发层，没有扩大删除范围、身份权限或 Agent 自主能力。

## 4. 源码级架构复核

### 4.1 从成熟开源项目借鉴的部分

Open WebUI 和 LibreChat 的代码共同表明，成熟对话产品通常把以下关注点拆开：

- 消息本身与消息动作能力；
- 会话/分支/删除 API 与前端按钮；
- 记忆 schema、治理接口和模型上下文注入；
- 知识文件、内容状态、检索索引、来源与访问控制；
- 工具声明、工具权限和实际副作用执行。

本项目只借鉴这些分层，不引入它们的通用 Agent runtime、插件系统、向量基础设施或多模型编排。

### 4.2 当前 NOVA 的准确边界

- **会话上下文**：`ai_messages` 只提供当前会话最近 20 轮、最长 30 天的有界原始历史；图片/文档是当前账号私有会话附件。
- **跨会话记忆**：`ai_memories` 只向模型注入用户确认偏好和带业务来源的稳定事实；旧 `ai_summary` 停止新写入和召回。
- **知识 RAG**：当前 10 篇审核发布文章和 17 条植物档案使用字段加权、中文词片、段落级选择和 `published-only` 门禁。
- **意图路由**：高置信域内/域外由代码决定，无法确信的表达可进入一次无业务权限的模型语义回退；不存在第二分类模型和模型工具循环。
- **选择功能**：是产品 launcher/服务端白名单上下文，不是运行时 tool calling。任务、诊断和记忆修改仍由用户确认页面完成。
- **身份**：会话、记忆、附件和 PlantPet 继续以 JWT openid 为所有权边界。

## 5. 记忆系统评估与本轮加固

### 5.1 当前不需要复杂记忆框架

NOVA 要解决的是植宠养护连续性，不是通用个人助理的开放长期画像。现在已经有三种清晰状态：

1. 账号称呼：唯一来源是 `users.nick_name`，每次按 JWT openid 读取，不复制成 AI 记忆；
2. 当前会话历史：有界、可恢复，但不冒充长期事实；
3. 结构化长期上下文：用户确认偏好或从档案/任务/日记/已保存诊断派生的带来源事实。

为了让现有系统从“有功能”变成可控的 MVP，本轮做了四项轻量加固：

- `ai_summary` 明确排除出模型上下文；
- 候选按用户确认、类型、本轮词项相关性和更新时间排序；
- 内容规范化去重，最多注入 8 条，避免把 80 条候选原样塞给模型；
- 只有已确认的 `user_preference` 能修改，且由 `api-scf` 后端强制；业务事实必须回原业务对象修改。

没有新增自动抽取偏好、模型自主写记忆、跨用户记忆、隐藏画像、重要度衰减模型或新记忆类型。

### 5.2 暂不上知识图谱

当前语料只有 17 条植物档案和 10 篇审核文章，主要问题是短路径的养护/知识检索，不存在必须沿“植物—症状—原因—任务—来源”多跳查询的稳定产品需求。知识图谱会提前引入实体消歧、关系抽取、版本一致性、错误关系纠正和运营维护，却不能直接提高当前三分钟比赛主流程。

只有满足以下任一条件才重新评审：

- 产品出现稳定 ID 的跨对象关系/路径查询；
- 需要解释任务或诊断如何沿多条来源和业务事件推导；
- 带标签评测证明关系检索能显著减少错误且维护成本可接受。

## 6. RAG 系统评估

当前不上向量数据库不是拒绝语义检索，而是没有证据证明它比小语料确定性检索更合适：

- 语料小、字段稳定、已有植物名/别名/问题类型/标题/段落等强词法信号；
- `published-only`、来源可见和数据库空集语义比“召回更多”更重要；
- 现有字段加权、中文词片和段落选择可通过确定性测试复现；
- 向量库会增加 embedding 生成、索引同步、删除一致性、阈值和混合排序运营。

本轮保留轻量 RAG，并用意图语料、真实 API smoke 和 E2E 防止域外检索、跨植物污染和无来源回答。后续只有在带标签查询集中稳定出现“语义相关但没有词项重合”的漏召回，或语料增长到数百/数千份异构文档时，才评审 hybrid retrieval。届时也应先建立离线 recall/precision、延迟和来源完整性基线，再决定 embedding 模型与索引，不先选技术后找问题。

## 7. 无限额度策略

按最新比赛决定，所有账户 Chat/Vision 都显示并执行无限额度：

- `getQuotaConfig()` 返回 `unlimited=true`，限额和剩余值为 `null`；
- Chat/Vision/文档合法请求不会因每日次数被拒绝；
- `ai_usage_daily` 仍累加次数和 token，保留成本/容量观测；
- 坏图、格式不一致、超过 2 MB 和非法文档仍在模型调用与用量记账前拒绝；
- 原来的 50/10 环境变量、429 分支和文档合同已移除。

这不是新增本地化妥协，也没有把 Key 放进前端。未来若要恢复限额，需要作为产品政策重新评审，而不是只改两个环境变量。
