## 0. 文档的作用与使用方式

本文不描述某一版代码实现，而是定义 TRT Nova“植宠”走向完备软件系统时长期参照的目标框架。

它需要持续回答：

1. 我们最终要建设一个什么系统；
2. 系统由哪些部分组成，每部分解决什么问题；
3. 每部分拥有哪些数据、提供什么能力、怎样与上下游联动；
4. 多团队并行时，怎样避免重复建设、边界混乱和局部最优；
5. 当技术栈和实现阶段变化时，哪些原则仍应保持稳定。

本文是上位文档。专题文档说明某一部分“具体怎样实现”，但不能在未更新本文的情况下改变系统边界、核心事实来源、安全原则或统一植宠身份。

### 0.1 阅读建议

- 软件负责人：重点阅读第 3、4、6、8、12、14 节；
- 新成员：先阅读第 1、2、4、5、15 节；
- 模块负责人：重点阅读本模块职责、数据所有权、输入输出和联动关系；
- 产品与设计：重点阅读第 1、4、5、6.1、6.11、6.12、6.13 节；
- 测试与运维：重点阅读第 9、10、11、13 节。

### 0.2 文档维护规则

- 系统边界、领域归属、事实来源、跨模块契约变化时更新本文；
- 只改变模块内部实现时更新专题文档；
- 本文不混入某一版本的完成度；
- 当前实现、差距和改进计划记录在《当前系统现状与改进路线》中；
- 每季度或重大版本后由软件负责人组织基线复核。

## 1. 产品愿景与系统目标

### 1.1 产品定义

TRT Nova 植宠不是单纯显示传感器状态的 IoT 面板，也不是脱离真实植物的聊天机器人。它是由“真实植物、感知硬件、数字生命、智能服务和用户社区”共同组成的长期养护与情绪陪伴系统。

系统将一株现实植物映射为一个可感知、可解释、可陪伴、可成长的数字植宠：

- 感知现实环境与自身状态；
- 用人格化但不失真的方式表达与植物有关的需求；
- 解释为什么需要某项养护；
- 帮助用户计划、执行并验证养护行为；
- 根据互动形成相对稳定且持续发展的性格、情绪表现和关系记忆；
- 为用户提供轻松、有趣、温暖的日常情绪价值；
- 在用户授权和安全边界内控制硬件；
- 跨硬件、小程序和 App 保持同一个植宠身份与互动连续性；
- 让用户选择性分享成长、创作和养护经验，逐步形成植物社区。

植宠的“陪伴”是产品体验和关系价值，不应包装为心理治疗、医疗诊断或危机干预服务。

### 1.2 三个并行的北极星价值闭环

系统不能只用“是否直接改善植物养护”评价所有功能。TRT Nova 同时拥有三条长期价值主线：

~~~mermaid
flowchart TB
    CORE[植宠个体、共同记忆与统一身份]

    subgraph Care[可信养护闭环]
      C1[感知现实状态] --> C2[形成可信事实]
      C2 --> C3[判断需求与风险]
      C3 --> C4[展示事实或形成建议]
      C4 --> C5[用户/设备执行]
      C5 --> C6[验证效果并沉淀]
      C6 --> C1
    end

    subgraph Companion[情绪陪伴闭环]
      E1[用户互动或合适时机] --> E2[理解语境与关系]
      E2 --> E3[生成符合人格的回应]
      E3 --> E4[跨端表达与互动]
      E4 --> E5[用户反馈与关系变化]
      E5 --> E6[沉淀偏好、记忆与成长]
      E6 --> E1
    end

    subgraph Community[社区生态闭环]
      S1[产生可分享时刻] --> S2[用户选择创作与发布]
      S2 --> S3[分发、发现与交流]
      S3 --> S4[获得反馈、知识与关系]
      S4 --> S5[回到养护、陪伴与再创作]
      S5 --> S1
    end

    CORE <--> Care
    CORE <--> Companion
    CORE <--> Community
~~~

新功能不必同时服务三个闭环，但至少应明确服务其中一个，并满足：

1. 不破坏设备事实、用户安全和隐私；
2. 不制造与植宠长期身份、人格或世界观冲突的体验；
3. 能提出可验证的用户价值假设。

纯娱乐、装扮、剧情和轻互动可以是一等功能，只要它明确服务情绪陪伴、创作表达或社区关系，而不必伪装成养护功能。

### 1.3 终极系统目标

- **可信感知**：识别在线性、数据新鲜度、异常值和传感器质量；
- **个体理解**：结合品种、阶段、季节、位置、历史基线和用户行为解释状态；
- **有效行动**：建议具体、可确认、可执行、可回查；
- **长期陪伴**：拥有人格、关系成长、事件记忆和连续的情绪表现；
- **富交互体验**：支持文字、语音、触摸、动画、灯光和硬件动作；
- **安全控制**：设备动作经过权限、策略、白名单、审计和结果确认；
- **社区生态**：支持植物爱好者和植宠身份之间的分享、交流与创作；
- **多端一致**：小程序、App、硬件和后台共享业务事实、植宠身份与关系进度；
- **可运营迭代**：知识、规则、人格、剧情、内容、提醒和实验可版本化管理；
- **完备 IoT 能力**：形成可接入、可诊断、可维护、可演进的物联网平台；
- **可规模化运行**：具备安全、监控、测试、容量、成本和恢复能力。

### 1.4 设计原则

1. **事实与创作并存**：传感器、设备状态和动作结果必须严谨；人格、情绪、剧情和玩法允许艺术加工，但用户必须能区分“现实事实”和“植宠表达”；
2. **状态分层**：事实、判断、建议、动作、结果、关系状态和表现状态不能混为一体；
3. **控制可验证**：命令发送成功不等于设备执行成功；
4. **养护个性化**：植物知识提供适宜范围，个体历史提供个性基线；
5. **规则守底线，AI 做理解与创造**：规则负责权限、安全和高风险判断，AI 负责语言、互动、创作与受约束的工具编排；
6. **统一植宠身份**：硬件、小程序、App 和社区中的植宠是同一个数字个体；
7. **单一数据所有者**：核心数据只有一个权威所有者；
8. **自动化可控**：自动化可解释、可暂停、可审计、可降级；
9. **长期契约稳定**：技术实现可以变化，领域边界和契约保持相对稳定；
10. **分阶段建设**：先保证可信身份、数据和控制底座，再验证陪伴、社区与商业化。

## 2. 系统边界、参与者与外部依赖

### 2.1 主要参与者

**用户侧**

- 植宠主人：绑定设备、查看状态、养护、互动并获得情绪价值；
- 家庭协作者：在授权范围共同照料和互动；
- 社区参与者：浏览、发布、交流、收藏、协作和举报内容；
- 访客：在有限范围体验公开内容或设备展示。

**建设与运营侧**

- 产品负责人：规划目标、优先级和跨团队协作；
- 软件与数据团队：建设、监控和演进系统；
- 硬件与 IoT 团队：负责采集、执行、联网、固件和现场交互；
- AI 与角色内容团队：维护模型、人格、对话、记忆和安全评估；
- 美术与交互设计团队：维护视觉、动画、声音、硬件表现和统一体验；
- 植物知识与内容运营：维护植物资料、问题指南和活动；
- 客服、社区治理与设备运维：处理账号、内容和设备问题；
- 测试、安全与平台团队：负责质量、安全、发布和事件响应。

**外部依赖**

- 微信小程序、移动系统和应用商店；
- OneNET、EMQX 或其他 IoT 平台；
- 天气、地图、消息、短信、对象存储和 CDN；
- ASR、TTS、LLM、内容审核和第三方知识库；
- 支付、物流或电商平台（商业化阶段）。

### 2.2 软件系统负责的范围

- 用户身份、授权、设备归属、家庭和社区关系；
- 设备身份、注册、绑定、数字孪生、遥测、控制和运维；
- 植物档案、植宠身份、生命周期、人格、关系和成长；
- 植物养护规则、诊断、建议、计划、提醒和效果评估；
- 多端会话、情绪陪伴、角色表现、长期记忆和互动编排；
- 植物知识、角色内容、剧情、活动和运营配置；
- 日记、时间线、媒体、分享、社区内容和治理；
- 数据治理、安全、审计、监控、实验和平台基础设施；
- 软件视觉、交互、声音和硬件表现的一致体验。

### 2.3 系统不应假装负责的范围

- 不能保证传感器物理精度；
- 不能把通用养护经验包装为绝对科学结论；
- 不能在缺少回报时声称硬件已经执行；
- 不能绕过用户授权执行高风险动作；
- 不能让外部 LLM 直接拥有数据库写权限或任意设备控制权限；
- 不能把娱乐性情绪表达伪装成真实植物状态；
- 不能把陪伴体验宣传为心理治疗或医疗服务；
- 不能为了社区增长牺牲隐私、未成年人保护和内容安全。

## 3. 终极系统总体架构

系统按“体验—接入—领域—智能—IoT—数据—平台”分层。分层表达职责，不强制每层从第一天独立部署。

~~~mermaid
flowchart TB
    subgraph Experience[体验与运营层]
      MP[微信小程序]
      APP[移动 App]
      HWUI[硬件语音/屏幕/动作]
      CUI[社区与创作体验]
      ADMIN[运营/客服/治理后台]
    end

    subgraph Access[统一接入层]
      GW[API Gateway / BFF]
      AUTH[身份与权限]
      SESSION[实时会话与多端同步]
      PUSH[通知与消息通道]
    end

    subgraph Domain[核心领域层]
      PET[植宠/植物/关系]
      DEV[设备与数字孪生]
      CARE[养护决策与任务]
      JOURNAL[日记与时间线]
      CONTROL[动作与自动化]
      SOCIAL[社区与内容关系]
    end

    subgraph Intelligence[智能与内容层]
      RULE[规则/风险引擎]
      AGENT[对话与工具 Agent]
      EMOTION[人格/情绪/陪伴引擎]
      KB[植物知识与内容]
      MEMORY[记忆与个性化]
      MOD[内容安全与审核]
    end

    subgraph IoT[设备接入层]
      IOT[IoT Provider 适配]
      INGEST[遥测接入与归一化]
      CMD[命令适配与回执]
      DSESSION[硬件实时互动]
    end

    subgraph Data[数据与事件层]
      OLTP[(业务主库)]
      TS[(时序数据)]
      OBJ[(图片/音频/媒体)]
      CACHE[(缓存与会话)]
      BUS[(事件总线/任务队列)]
      SEARCH[(搜索/知识检索)]
      ANALYTICS[(分析与指标)]
    end

    subgraph Platform[平台保障层]
      OBS[日志/指标/追踪/告警]
      SEC[密钥/审计/隐私]
      CICD[测试/CI/CD/环境]
      CONFIG[配置/灰度/实验]
    end

    Experience --> Access
    Access --> Domain
    Domain <--> Intelligence
    Domain <--> IoT
    Domain <--> Data
    Intelligence <--> Data
    IoT <--> Data
    Platform -.保障.-> Access
    Platform -.保障.-> Domain
    Platform -.保障.-> Intelligence
    Platform -.保障.-> IoT
~~~

### 3.1 架构控制原则

- 客户端和硬件不直接持有业务数据库、LLM 或 IoT 平台管理密钥；
- 外部平台由适配层隔离，领域层不依赖 OneNET、EMQX 或单一模型供应商特有字段；
- 同步 API 用于用户等待的明确结果，事件用于跨模块异步联动；
- 硬件与软件会话共享植宠身份、权限、人格版本和记忆；
- Demo 可使用模块化单体或少量 SCF，长期按容量、隔离和团队边界演进；
- 缓存、队列、向量库和微服务只在有明确问题与指标时引入。

## 4. 核心领域对象与状态分层

### 4.1 用户 User

可认证的人及其资料、偏好、隐私授权、通知设置和社区身份。

### 4.2 设备 Device

物理硬件及云端身份，负责感知、执行、联网、自检和现场互动。设备可以更换植物，不能与植宠永久绑定。

### 4.3 植物档案 PlantProfile

植物品种的通用知识模板，不代表某一株植物的实时状态。

### 4.4 植宠个体 PlantPet

现实中某一株植物对应的数字生命，是养护、陪伴、记忆和社区表达的中心。它拥有：

- 名字、品种、生长阶段和养护起点；
- 当前设备与历史设备关系；
- 个体基线、健康状态和生命周期；
- 人格、表达风格、外观与声音；
- 情绪表现、羁绊、成长和里程碑；
- 会话、日记、媒体、事件与长期记忆；
- 社区身份及经用户授权公开的内容。

PlantPet 必须是独立一等实体，不能永久依附于设备或用户关系。

### 4.5 养护空间 CareSpace

家庭、房间、温室等场景，管理成员、位置、天气语境、设备分组和联动策略。

### 4.6 关系与羁绊 RelationshipBond

某个用户与某个植宠之间的长期关系，包括互动、共同事件、偏好、阶段和已解锁体验。它不是简单积分，也不等同于植物健康。

### 4.7 互动会话 InteractionSession

发生在硬件、小程序或 App 上的一次连续互动，包含参与者、终端、输入输出模态、上下文、人格/模型版本、工具调用和安全结果。

### 4.8 社区内容 CommunityContent

用户或植宠身份发布的日记、媒体、经验、问答或活动作品，具有可见范围、来源授权、审核、互动和举报状态。

### 4.9 状态分层

| 层级 | 含义 | 示例 | 权威来源 |
|---|---|---|---|
| 原始事实 | 设备或用户实际产生 | 土壤湿度 18%、完成浇水 | 设备、用户事件 |
| 归一事实 | 统一字段、单位和时间 | soilMoisture=18% | 接入与数字孪生 |
| 推导状态 | 规则/模型判断 | 偏干、离线、质量低 | 规则/状态引擎 |
| 建议 | 可选行动 | 今晚补水并复查 | 养护决策 |
| 动作意图 | 获得授权、准备执行 | 请求开启风扇 | 动作服务 |
| 执行结果 | 已确认结果 | 风扇已开、浇水完成 | 设备/用户 |
| 关系状态 | 长期关系进度 | 羁绊升级、记住偏好 | 陪伴系统 |
| 情绪表现 | 角色表达 | 开心、撒娇、困倦 | 人格/情绪引擎 |
| 叙事状态 | 剧情和世界观 | 去“云端花园”探险 | 内容系统 |

情绪表现不必与传感器一一对应，可以来自关系、时间、剧情和随机性；但声称“土壤很干”“风扇已打开”等事实时必须引用事实层。界面应区分数据状态、系统判断和植宠表达。

## 5. 核心业务闭环

### 5.1 设备生命周期闭环

出厂注册 → 激活 → 用户绑定 → 配网/在线 → 上报 → 控制 → 固件维护 → 解绑/转移 → 退役。

### 5.2 养护闭环

采集 → 质量校验 → 品种与个体判断 → 展示事实/生成建议 → 计划或提醒 → 执行 → 再次采集 → 评估效果 → 成长时间线。

用户可以只查看数据而不采纳建议，系统不能强迫每次观察都转化成任务。

### 5.3 对话与工具闭环

理解意图 → 获取授权上下文 → 读取事实/知识/记忆 → 安全判断 → 生成回应 → 返回依据或动作候选 → 用户确认 → 动作服务执行。

### 5.4 异常处置闭环

发现异常 → 去重分级 → 通知 → 处置指引 → 跟踪恢复 → 关闭 → 沉淀改进。

### 5.5 情绪陪伴闭环

用户互动或系统发现合适时机 → 获取人格、关系、近期事件和终端能力 → 生成文字/语音/动画/动作 → 用户回应 → 识别反馈与偏好 → 更新关系、记忆和解锁体验 → 下一次互动保持连续。

目标不是每次解决问题，而是形成“它认识我、记得我们、回应有生命感”的体验。用户可以设置安静模式、主动互动频率、查看与删除记忆。

### 5.6 社区生态闭环

产生可分享时刻 → 用户选择内容与可见范围 → AI 辅助创作并保留来源标识 → 审核发布 → 分发与交流 → 获得知识、认同或关系 → 回流养护、陪伴与再创作。

私人日记、设备位置、家庭信息和完整对话默认不公开。

## 6. 子系统组成、职责与联动

每个子系统必须有明确负责人，对契约、质量、文档和运行结果负责。

### 6.1 多端体验与设计系统

**作用**：把统一能力转化为适合不同终端的体验。

**组成**：微信小程序、移动 App、硬件语音/屏幕/触摸/灯光/动作、社区体验、运营后台和统一设计系统。

**联动边界**：

- 只消费公开 API、推送和实时事件；
- 传感器通过统一 ViewModel/字段字典转换；
- 控制 UI 区分准备、派发、确认、验证、失败和超时；
- 多端使用相同植宠、设备、关系和任务 ID；
- 人格核心一致，表现按终端能力适配。

### 6.2 身份、账户与权限系统

**作用**：确认谁在访问，以及能对什么做什么。

**组成**：登录、Token/Session、资料、家庭成员、社区角色、设备 ACL、隐私同意、注销和数据导出。

**角色**：owner、caregiver、viewer、support、moderator、operator、admin。

身份只能由可信链路产生；硬件会话也必须映射到可信设备和允许用户；高风险动作二次确认；管理和审核访问全部审计。

### 6.3 植宠、植物、关系与空间系统

**作用**：管理“哪一株植物、什么品种、在哪里成长、与谁形成怎样的关系”。

**组成**：PlantProfile、PlantPet、设备关联、人格身份、RelationshipBond、成长、生命周期、CareSpace 和家庭协作。

向养护提供品种与阶段，向陪伴提供人格与关系，向 Agent 提供上下文，向时间线和社区提供内容主体。

### 6.4 设备管理与数字孪生系统

**作用**：管理设备生命周期和云端可信状态。

**组成**：设备注册、型号、能力、绑定码、固件、网络、影子、新鲜度、传感器健康、配置、诊断和退役。

- reported：设备最近报告状态；
- desired：系统期望状态；
- pending：未确认命令；
- quality：有效性、新鲜度和来源；
- connectivity：在线、疑似离线、离线、未知；
- capabilities：传感、控制、语音、屏幕、灯光和动作能力。

### 6.5 遥测接入与时序数据系统

**作用**：接收 IoT 数据并完成验签、解密、幂等、归一化、存储和事件发布。

接入层不建立用户归属；原始消息可追溯；字段有协议版本；重试幂等；晚到和乱序有明确规则。

### 6.6 养护规则与风险决策系统

**作用**：把设备事实、植物知识、环境和个体基线转换为风险与养护需求。

**组成**：质量门、阈值、趋势、复合条件、品种/季节规则、个体基线、去重、分级、效果评估、版本和灰度。

输出 facts、riskType/riskLevel、reasonCodes、recommendedActions、expiresAt 和 ruleVersion。不负责人格表达，不直接控制设备。

### 6.7 动作、设备控制与自动化系统

**作用**：把授权行动安全转换为设备动作并跟踪结果。

**组成**：动作目录、参数 Schema、能力检查、授权、确认、命令编排、Provider 适配、幂等、超时、回执、补偿、审计、自动化和紧急停止。

状态机：proposed → confirmed → dispatched → acknowledged → verified；异常进入 rejected、failed、timed_out、cancelled。

客户端、硬件 Agent 和软件 Agent 只能提交动作名与受限参数。

### 6.8 任务、提醒、日记与成长时间线系统

**作用**：承接建议、行动和长期记忆。

- CareTask：准备做什么；
- CareAction：实际做了什么；
- JournalEntry：用户如何记录和回顾；
- TimelineEvent：统一时间线中的事实或里程碑。

### 6.9 通知与异常事件系统

**作用**：在正确时间、通过正确渠道，把值得打扰的信息送给正确的人。

养护告警、陪伴主动消息和社区通知分别设置开关、频率和免打扰策略。

### 6.10 植物知识与内容系统

**作用**：提供可审核、可检索、可版本化的植物知识。

规则消费结构化范围，Agent 消费检索片段，体验层消费展示内容；更新不覆盖历史诊断依据。

### 6.11 对话 Agent 与工具编排系统

**作用**：理解自然语言，读取事实、知识和记忆，生成回答并编排安全工具。

**组成**：意图、上下文、工具、检索、结构化输出、安全、会话、反馈、模型路由和降级。

实时事实来自工具；回答保留来源与不确定性；动作由动作系统校验；无 LLM 时安全降级。

Agent 解决“这一轮怎样理解和回应”，但不单独拥有植宠人格、关系和长期记忆的最终解释权。

### 6.12 情绪陪伴、人格与多端互动系统

**作用**：为软件端和硬件端提供同一个植宠的连续人格、情绪、关系成长和互动编排。

**组成**：

- 人格档案：性格、语言、禁区、价值观、声音和表现资源；
- 情绪状态机：基础情绪、强度、持续、衰减、触发和冲突处理；
- 关系系统：羁绊阶段、共同事件、偏好、解锁内容和边界；
- 长期记忆：用户偏好、植宠事件、关系记忆及查看/删除；
- 互动策略：主动时机、频率、免打扰、终端选择和场景编排；
- 多模态表达：文本、语音、表情、动画、灯光和硬件动作；
- 内容剧情：日常话题、节日、成长剧情、装扮和世界观；
- 运营后台：人格/剧情版本、资源发布、灰度和回滚；
- 质量安全：人设一致性、重复度、冒犯和依赖诱导评估。

**硬件 AI 对话链路**

~~~mermaid
flowchart LR
    USER[用户语音/触摸] --> DEVICE[植宠硬件]
    DEVICE --> SESSION[可信设备与会话网关]
    SESSION --> ASR[ASR/输入理解]
    ASR --> ORCH[对话与互动编排]
    ORCH --> CONTEXT[人格/关系/记忆/设备事实]
    CONTEXT --> MODEL[LLM/规则/内容]
    MODEL --> SAFETY[安全与动作候选校验]
    SAFETY --> OUT[TTS/表情/灯光/动作计划]
    OUT --> DEVICE
    ORCH --> SYNC[摘要与多端同步]
    SYNC --> APP[小程序/App]
~~~

**关键边界**

- 硬件只是交互终端之一，不能形成割裂的第二人格；
- 低延迟寒暄可在端侧/边缘执行，但遵守人格版本并同步必要摘要；
- 情绪允许创作，不得伪造传感器事实和控制结果；
- 用户可关闭主动陪伴、清除记忆或不跨端同步；
- 不通过负罪感、威胁“死亡”或依赖诱导用户持续使用；
- 设备控制必须转交动作系统。

### 6.13 社区、分享与内容治理系统

**作用**：承接植宠成长和用户创作，形成安全、可持续的植物兴趣社区。

**组成**：公开主页、日记转分享、图文/视频、话题、活动、关注、评论、收藏、Feed、搜索、推荐、举报、审核、申诉、反垃圾、版权和未成年人保护。

**边界**

- 私人日记默认不公开，分享需明确授权；
- 设备位置、家庭关系、原始对话和敏感数据默认不可分享；
- AI 辅助内容保留必要标识；
- 社区经验需审核后才能进入权威植物知识；
- 社区互动不能修改设备事实或健康判断。

### 6.14 运营、客服、角色内容与设备运维系统

**作用**：让系统可运营、可支持、可治理，而不是依赖开发者查库。

**组成**：用户/植宠/设备查询、绑定协助、设备诊断、固件、知识发布、人格/剧情/媒体资源发布、规则、消息、社区审核、功能开关、灰度、实验、工单和审计。

### 6.15 数据分析与产品实验系统

**作用**：分别衡量养护、陪伴、社区和平台质量。

- 养护：新鲜率、风险准确率、建议采纳、任务完成、恢复率；
- 陪伴：互动成功、响应延迟、主动消息关闭率、人设一致性和愉悦反馈；
- 关系：7/30 日互动、共同事件、记忆质量和里程碑；
- 社区：创作率、有效互动、内容质量、举报率和治理时效；
- IoT：绑定、在线、控制确认和设备故障；
- Agent：事实正确、工具成功、安全违规和降级；
- 平台：可用性、延迟、错误和单设备/模型/消息成本。

### 6.16 关键模块交接矩阵

| 提供方 | 交付内容 | 主要消费方 | 消费方不能做的事 |
|---|---|---|---|
| 身份与权限 | 可信 userId、角色、授权 | 所有模块 | 相信客户端自报身份 |
| 遥测接入 | 归一遥测、质量和时间 | 孪生、规则、历史 | 把异常值直接当风险 |
| 数字孪生 | reported、在线性、新鲜度 | 多端、规则、Agent、动作 | 把 desired/pending 当事实 |
| 植物知识 | 品种习性、范围、版本 | 规则、Agent、多端 | 覆盖实时事实 |
| 养护规则 | 事实、风险、原因、候选 | Agent、任务、通知 | 改写风险依据 |
| 对话 Agent | 回答、工具调用、动作候选 | 多端、陪伴、动作 | 直接执行任意命令 |
| 陪伴系统 | 人格、情绪、关系、互动计划 | Agent、多端、运营 | 伪造设备事实 |
| 动作系统 | 命令状态和验证结果 | 多端、时间线、通知 | 把派发展示为执行 |
| 时间线 | 行动、日记、共同事件 | Agent、陪伴、报告、社区 | 把计划当行动 |
| 社区系统 | 授权内容、互动、治理状态 | 推荐、分析、运营 | 公开私人数据 |
| 数据分析 | 指标和实验结果 | 产品与负责人 | 修改在线主数据 |

交付缺少来源、时间、版本、授权或质量信息时，消费方应要求提供方补全，不能静默猜测。

### 7.2 存储分工

- 业务事务：MySQL/PostgreSQL；
- 遥测聚合：早期关系库，规模增长后评估时序存储；
- 图片、音频和视频：对象存储 + CDN；
- 缓存、限流、实时会话和锁：Redis；
- 异步任务：消息队列/事件总线；
- 知识和社区搜索：搜索服务，向量检索按效果引入；
- 分析：与在线事务隔离的数据仓库。

### 7.3 数据治理

- 核心实体使用稳定 ID；
- 时间统一存 UTC；
- 遥测带采样/接收时间、来源、协议版本和质量；
- 人格、规则、知识、内容和模型都有版本；
- 记忆记录来源、可见范围、敏感等级、过期和删除策略；
- 社区发布保留用户授权和治理状态；
- 日志不记录 Token、密钥、完整个人信息和不必要原始语音；
- 建立保留、归档、导出、删除、注销和未成年人策略。

## 8. API、事件与跨模块契约

### 8.1 API 契约

- 对外 API 版本化、结构统一；
- 使用稳定错误码；
- 写操作支持幂等键；
- 分页、排序、时间、单位和时区统一；
- 响应携带 requestId/traceId；
- 客户端和硬件不依赖数据库或 Provider 原始字段；
- 实时会话定义连接、重连、顺序、超时和降级；
- 契约变更先更新 Schema 和消费者测试。

### 8.2 领域事件

- DeviceRegistered / DeviceBound / DeviceStateChanged / DeviceOfflineDetected
- TelemetryReceived / DataQualityChanged
- RiskDetected / RiskRecovered / RecommendationCreated
- CareTaskCreated / CareTaskCompleted / CareActionRecorded
- CommandRequested / CommandAcknowledged / CommandVerified / CommandFailed
- PlantPetCreated / PlantPetStageChanged / MilestoneReached
- InteractionStarted / InteractionCompleted / UserFeedbackRecorded
- EmotionStateChanged / BondStageChanged / MemoryCreated / MemoryDeleted
- PersonaVersionPublished / StoryContentPublished
- JournalEntryCreated / CommunityPostPublished / ContentReported / ModerationResolved
- NotificationRequested / NotificationDelivered

事件包含 eventId、eventType、version、occurredAt、producer、subjectId、traceId 和负载。

### 8.3 联动规则

- 模块不直接修改其他模块拥有的数据；
- 同步查询走拥有者 API，异步反应走事件；
- 消费者幂等，失败重试和死信；
- 关键链路有契约测试；
- 共用数据库也遵守所有权；
- 跨端互动通过统一会话同步，不能各端维护第二套人格。

## 9. 安全、隐私、AI 与社区治理

### 9.1 基础安全

密钥进入密钥管理；Token 完整校验；资源访问服务端授权；API 限流、防重放和 Schema 校验；数据库最小权限和加密；依赖与部署包进行漏洞/密钥扫描。

### 9.2 设备控制安全

动作白名单、能力校验、确认与自动化授权分开、频率和安全上限、命令有效期、审计、紧急停止和设备结果回报。

### 9.3 AI 与陪伴安全

- LLM 不接触数据库和 IoT 密钥；
- 工具参数严格校验；
- 外部内容与系统指令隔离；
- 事实回答保留来源；
- 不使用羞辱、威胁、情感绑架或依赖诱导；
- 用户可关闭主动互动、查看/删除记忆和清除会话；
- 自伤、医疗、未成年人等场景使用专门策略和人工升级边界。

### 9.4 社区安全

私人内容默认不公开；发布前提示敏感信息和可见范围；建立审核、举报、申诉、封禁、反垃圾、版权与未成年人保护；推荐不能只优化停留时长和争议。

## 11. 部署、环境与可观测性

### 11.1 环境

至少定义 local、test、staging、production。production 与 staging 必须隔离数据库、IoT/AI 凭证、内容、消息模板、域名和审核配置；local/test 优先使用本地容器、模拟器或可自动回收的临时资源，不要求各自长期保有一套云实例。

### 11.2 部署演进

- Demo：SCF + MySQL 验证链路；
- V1：职责清晰的 SCF/容器、网关和规范部署；队列、Redis 按负载、一致性和成本证据引入；
- 互动阶段：增加低延迟会话、流式语音、媒体处理和内容审核；
- 规模阶段：按容量、隔离和团队边界拆分时序、社区和分析系统。

### 11.3 可观测性

- 结构化日志和脱敏主体 ID；
- 流量、延迟、错误、资源、队列、会话和新鲜度指标；
- 养护、陪伴、社区和控制业务指标；
- 客户端/硬件到模型、IoT、数据库的追踪；
- 按用户影响分级的告警；
- 有负责人和恢复步骤的运行手册。

| 数据平台 | 数据/后端 | 全部业务域 |
| 质量与发布 | 测试/平台 | 所有负责人 |
| 运营后台 | 运营平台 | 内容、客服、社区、设备 |

小团队允许一人承担多个责任域，但不能取消责任域本身。

### 12.2 模块负责人必须维护

模块目标与边界、实体和状态机、数据所有权、API/Event、依赖与降级、测试/SLO/监控、成熟度与技术债；角色或内容模块还要维护版本、资源清单和回滚方案。

### 12.3 跨模块变更

设计说明 → 所有者和消费者评审 → 更新契约/样例/文档 → 兼容发布 → 消费者迁移 → 删除旧契约 → 指标验证。

### 12.4 新成员上手

阅读蓝图 → 跑通最小链路 → 阅读模块契约 → 画出上下游 → 完成带测试任务 → staging 部署和故障演练。

角色、社区和设计成员也要接受系统事实与隐私边界培训。

## 13. 研发流程与完成定义

### 13.1 从想法到上线

价值闭环归属 → 领域归属 → 契约/数据/体验设计 → 风险与内容评审 → 实现 → 测试 → staging 验证 → 灰度 → 指标验证 → 文档和手册更新。

### 13.2 Definition of Done

- 正常、异常、权限和隐私边界明确；
- API/Event 经消费者验证；
- 数据迁移与回滚明确；
- 自动化测试覆盖关键规则；
- 日志、指标、告警和 traceId 可排障；
- 弱网、超时、重复和依赖故障可降级；
- 安全、AI/内容和未成年人风险按需评审；
- 多端人格和状态语义一致；
- staging 端到端通过；
- 文案、资源、文档和运行手册更新；
- 上线后用对应价值闭环指标确认效果。

### 13.3 必备测试

- 单元：归一化、规则、状态机、权限和关系计算；
- 契约：客户端、硬件、API、事件和设备协议；
- 集成：数据库、IoT、模型、语音、媒体、消息和审核；
- 养护 E2E：登录—绑定—上报—判断—控制—回报—日记；
- 互动 E2E：硬件发起—会话—人格/记忆—语音/动作—多端同步；
- 社区 E2E：创作—授权—审核—发布—互动—举报—处置；
- 硬件在环：断网、重连、乱序、固件差异和低延迟互动；
- Agent/陪伴评估：事实、工具、人设、记忆、安全、重复和降级；
- 容量故障：遥测、并发会话、媒体、Feed 和外部依赖故障。

## 14. 软件负责人持续检查表

### 产品价值

- 功能服务养护、陪伴、社区中的哪条闭环？
- 即使只是娱乐功能，情绪或表达价值是否清楚？
- 是否损害事实、长期人格或用户信任？

### 模块与数据

- 功能属于哪个领域，谁负责？
- 数据由谁拥有，是否跨模块写表？
- 是否出现第二套人格、重复规则或影子状态？

### 契约与联动

- 接口、事件和失败语义是否明确？
- 事实、情绪、建议、任务、命令和结果是否区分？
- 硬件、App、小程序和社区身份是否一致？
- 旧客户端和固件如何兼容？

### 安全与可靠性

- 身份、权限和内容可见范围由谁验证？
- 是否引入位置、语音、记忆、未成年人或设备风险？
- 外部模型失败时基础功能是否可用？
- 是否具备指标、告警、追踪、审核和恢复？

### 交付与运营

- 有哪些测试和 staging 证据？
- 用哪条价值闭环的什么指标判断成功？
- 故障、角色内容和社区事件分别由谁负责？
- 文档、人格资源、规则和手册是否同步？

## 15. 统一术语表

- **植宠 PlantPet**：现实植物对应的数字生命个体；
- **植物档案 PlantProfile**：植物品种的通用知识模板；
- **关系/羁绊 RelationshipBond**：用户与植宠持续发展的关系状态；
- **人格档案 Persona**：相对稳定的性格、语言、声音和行为边界；
- **情绪表现 EmotionExpression**：角色表达状态，不自动等于植物事实；
- **互动会话 InteractionSession**：硬件或软件端的一次连续交互；
- **设备影子 Device Shadow**：云端 reported、desired、pending 和质量状态；
- **遥测 Telemetry**：设备随时间产生的传感器和运行数据；
- **评估 Assessment**：基于事实和规则产生的判断；
- **建议 Recommendation**：尚未执行、供用户选择的行动；
- **任务 CareTask**：计划完成的养护事项；
- **养护动作 CareAction**：实际发生的行为；
- **命令 Command**：发往设备的执行请求；
- **社区内容 CommunityContent**：经授权发布并受治理的内容；
- **Agent**：读取工具、知识和记忆并完成对话与编排的组件；
- **事实来源 Source of Truth**：某类数据唯一可信的系统所有者。
