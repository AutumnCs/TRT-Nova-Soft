## 1. 当前产品链路

M6 继续使用现有四 Tab 中的“AI 助手”，不新增云部署单元：

- 小程序 `pages/assistant` -> `AgentService` -> `agent-scf /agent/session`、`/agent/chat`、会话 list/create/fork/withdraw、`/vision/analyze`、`/vision/mark-saved`、`/document/analyze`
- `agent-scf` -> 已发布知识、PlantPet 事实、养护事件、成长日记、结构化记忆和 OpenAI-compatible Chat/Vision API
- 小程序在用户主动确认后 -> `AgentService` -> `api-scf /ai/diagnosis-save` 或 `/care/task-create`
- `pages/aiMemory` -> `api-scf /ai/memor*` -> MySQL `ai_memories`
- 图片/文档发送 -> `MediaStorageService` -> 当前本地媒体 provider 的私有 `conversation_image`/`conversation_document`；用户另存观察记录后才写 `plant_diagnoses`

Agent 只读取业务事实并生成建议候选，不直接写任务、档案或日记。任务候选还必须先通过“用户明确要求安排/创建/提醒/制定任务”的确定性意图门禁，再进入可编辑表单，最后沿 `api-scf` 的既有 `confirmed=true` 约束写入。成功发送的图片作为当前账号私有的有界会话附件保存；它不会自动成为某个 PlantPet 的诊断或观察记录，后者仍只有用户点击“另存为观察记录”后才写入。

当前 NOVA 的准确架构定性是“受控的单 Agent/LLM 工作流”：确定性代码负责身份、用量记录、上下文、植物主题、RAG、记忆和副作用门禁，回答分支至多执行一次模型调用。它没有自主工具循环、多 Agent、handoff、subagent、checkpoint 或运行时 Agent harness。上层结构、权责和评测 harness 见 [M6 NOVA Agent 架构与验收 Harness](./m6-agent-architecture-and-harness.md)。

当前扩展入口位于消息输入框旁的“+”。一级菜单为“添加附件 / 选择功能”；附件二级菜单提供拍照、相册和文档，功能二级菜单只列当前真实存在的只读能力与确认式页面入口。页面没有单独占据顶部空间的 Vision 按钮。消息默认态不显示操作控件；长按本人用户消息后，才在气泡附近显示临时的图标加文字菜单，并按权限提供复制、重新编辑和最后一轮撤回。重新编辑适用于纯文字和已保存原件的图片/文档消息，原文字与原附件会回填 composer；重新发送始终创建新分支并保留原会话。旧版缺少永久媒体标识的附件消息不显示无法完成的重新编辑。菜单不占消息流高度，点空白、滚动、切换页面或完成动作后关闭。编辑状态缩为 composer 顶部单行 chip。长回答只滚动消息区，输入框持续可见。开发者工具键盘约定为 Enter 发送、Shift+Enter 换行。

```dotenv

LLM_API_PATH=/chat/completions
LLM_API_KEY_FILE=D:/植宠项目/API-key.txt

LLM_TIMEOUT_MS=30000
LLM_MAX_TOKENS=700
VISION_MODEL=deepseek-v4-flash-vision-exp
VISION_IMAGE_DETAIL=low
VISION_TIMEOUT_MS=30000
```

`D:\植宠项目\API-key.txt` 是本地开发阶段的临时凭证文件。只记录路径，不把正文复制到源码、Git、前端、文档或日志。本地 Chat 与 Vision 共用这一套本地凭证。DeepSeek 官方文档当前将 `https://api.deepseek.com` 作为 OpenAI-compatible base URL，并列出 `deepseek-v4-flash` 与可接受图片输入的实验模型 `deepseek-v4-flash-vision-exp`；本实现仍以真实 API 冒烟为准，不仅凭模型名称宣称可用。

## 3. 数据、保留、无限策略与用量

`reference/ai_assistant.m6.sql` 增加以下正式业务结构：

- `ai_conversations`：按 JWT openid、会话键和可选 PlantPet 归属会话。
- `ai_messages`：原始用户/助手消息与结构化响应；每会话最多保留最近 40 条消息，即 20 轮，同时清理超过 30 天的原始消息。
- `media_objects(purpose=conversation_image)`：成功发送的私有会话图片；以消息 id 建立有界引用，消息因 20 轮或 30 天规则被裁剪前同步删除对应图片。Base64 和微信临时路径不写入会话表。
- `media_objects(purpose=conversation_document)`：成功分析的 TXT/MD/CSV/JSON/PDF/DOCX 原件引用；提取文本只进入本轮模型请求，不写长期记忆或知识库。当前单文件上限 1 MB。
- `ai_memories`：`plant_fact`、`business_event`、`user_preference`、`ai_summary` 四类结构化记忆，保留来源、来源时间和用户确认状态。
- `plant_diagnoses`：候选、可见迹象、可能原因、建议、补拍问题、模型版本和用户修正。
- `ai_usage_daily`：Asia/Shanghai 自然日的 Chat/Vision 次数和模型 token 用量。

当前比赛阶段所有账户的 Chat/Vision 都是无限额度。`ai_usage_daily` 继续按 Asia/Shanghai 自然日记录调用次数和模型 token 用量，供本地观测与未来容量评估，但不再拒绝请求，也不再读取 `AI_CHAT_DAILY_LIMIT` / `AI_VISION_DAILY_LIMIT`。坏图片、格式不一致和超过 2 MB 的图片仍在模型调用及用量记账前拒绝，不伪造模型结果。

结构化记忆页支持按植宠筛选、查看来源和时间、添加用户确认偏好、修正、逐条删除和限定当前筛选范围清空。清除记忆不会删除 PlantPet、任务、日记或原始业务事实；后续再次进入助手时，仍可从现有业务事实重新生成对应记忆。

## 4. Chat 植物主题边界

当前选中的 PlantPet 提供个体档案、历史和记忆，但不能覆盖用户本轮明确写出的植物名。后端先用已发布植物档案解析本轮显式植物主题：

- 本轮没有明确植物名时，继续使用当前 PlantPet 上下文。
- 本轮植物与当前 PlantPet 一致时，继续正常生成 RAG 回答；只有本轮还包含明确的任务安排意图时，才生成待确认任务候选。
- 本轮植物与当前 PlantPet 不一致时，代码确定错配并隔离上下文；现有同一次 Chat 调用用 NOVA 的自然口吻说明“当前选中植物”和“本轮询问植物”，RAG 改用本轮植物，只展示它的已发布来源。模型不可用或回答漏掉两个植物主题时，代码补一条简短兜底说明。
- 错配时不生成任务候选、不显示任务预览按钮，也不把其他植物的回答保存为当前 PlantPet 的 `ai_summary`；原始会话仍保留本轮问题和边界提示用于追溯。
- 用户切换到对应 PlantPet 后，才恢复绑定该植宠的可编辑任务候选。

该规则不依赖模型自行遵守：错配判断、当前 PlantPet 私有上下文隔离、来源过滤、任务阻断和结构化记忆阻断都由 `agent-scf` 确定性执行。模型只在原有一次回答调用中负责自然措辞；没有新增第二次 LLM 分类或改写调用。

职责域采用三态级联。明确养护、一般植物定义、状态、植物知识、识别/记录等请求进入 `in_scope`；明确算式、证明、纯创作、敏感记忆与非植物任务进入 `out_of_scope`，不启动 RAG 或 Chat；规则无法确定的表达进入 `deferred`，可使用现有一次 Chat 自然回应，但不提供 PlantPet 私有上下文、RAG、任务候选或 `ai_summary` 写入。因而“月季是什么/介绍一下月季”会直接进入月季知识回答，`1+2 是多少个月季/玫瑰`、纯写诗、编程、`帮我记住密码`、`给服务器安排观察任务` 仍在模型前停止，单独输入一个植物名则由无权限语义回退澄清方向。

“我是谁/我叫什么”等账号称呼问句在植宠上下文、记忆、RAG 和模型之前进入确定性分支，只按 JWT openid 执行 `SELECT nick_name FROM users WHERE openid = ? LIMIT 1`。资料存在时 NOVA 只把它称为账号昵称，不冒充真实身份；资料为空或暂不可读时如实说明，并引导到“我的 → 个人资料”。“我叫/以后叫我/请记住我叫……”同样不调用模型，不自动修改账号资料或 `ai_memories`，只说明显式保存路径。所有分支都提示不要提交手机号、证件号或账号密码；原始问答仍可恢复页面记录，但会从后续养护模型历史中排除。

NOVA 面向用户时先自然回答问题，语气保持温和、耐心、诚实；证据不足时直接说不确定。回答不把“知识库、RAG、已复核发布、模型配置、任务绑定”等实现与治理术语当作产品人设，也不逐字段照抄内部资料卡。

## 5. Vision 边界

用户从输入区“+”选择相机或相册。选择完成后图片只进入本地 composer 草稿，展示缩略图、大小和移除入口；此时不调用 Vision、不上传也不弹出第三方处理同意。当前一次只支持一张待发送图片，用户可以只发图片，也可以继续填写文字，最后由同一个发送动作提交。第一次真正发送图片前，页面明确告知：图片将发送给第三方 AI 服务做分析，并作为当前账号的私有会话附件保存；只有用户另行确认时才把结构化观察另存到具体 PlantPet。这个产品边界变化使用告知版本 `nvp_vision_notice_ack_v2`，不会沿用旧版“原图不保存”的同意记录。

小程序按图片实际字节识别 JPEG、PNG 或 WebP，不依赖微信临时文件是否带扩展名；后端再次校验内容与声明一致且容器完整，单张上限 2 MB。可选配文通过现有 `/vision/analyze` 的 `message` 字段随图片进入同一次模型请求；Vision 不转入通用 Chat 工具循环。输出必须结构化为：

- 是否为植物与不确定状态；
- 针对随图配文的自然 NOVA 回复；
- 最多 3 个品种候选、0–1 置信度和可见依据；
- 图片中可见迹象；
- 使用“可能”语义的原因与证据；
- 当前建议动作；
- 需要补拍的问题；
- 非植物原因或模型不可用时的明确手动路径。

模型输出不是确定性病害诊断。没有足够图像证据时保留不确定，不把 PlantPet 上下文覆盖为图片事实。

Vision 成功后，后端在同一个数据库事务内保存配文、结构化观察、模型版本和会话图片引用；切换页面或重新进入助手后，无需先保存诊断也能恢复原图、配文和分析。媒体读取继续按 JWT openid 校验，图片随对应消息的 20 轮/30 天裁剪同步清理。原始 Base64 和微信临时文件路径不会进入 `ai_messages`；如果模型调用失败，客户端只清理仍未被消息认领的临时上传。用户明确点击“另存为观察记录”后，诊断仍沿既有业务接口写入，`/vision/mark-saved` 只把该诊断 id 和诊断媒体 id关联到本人对应的助手消息，不替换原有会话图片。这个流程不新增记忆类型，也不允许 Agent 自动保存诊断。

Vision 返回的 `advice` 只是自然语言养护建议，不能自行变成任务。图片任务候选同时要求：本轮文字包含明确的安排/创建/提醒/制定意图、存在当前 PlantPet、图片候选置信度至少 0.7，且候选名称与当前 PlantPet 的物种或昵称匹配。任一条件不满足时只回答和展示建议，不生成任务卡。这里没有 LLM `tool call`：模型既不选择工具也不执行工具；后端代码最多准备一个候选，实际任务仍必须经可编辑表单和 `confirmed=true`。

### 验收返工根因

- “图片分析没有完成”的真实根因是微信临时图片路径可能没有扩展名，旧前端因此默认把实际 PNG 声明为 JPEG；后端正确拒绝了“内容与声明不一致”。当前改为按图片字节识别 MIME，前后端双重校验仍保留。
- 本轮用户反馈的那次手工失败没有保留可与之对应的 `/vision/analyze` 请求日志，因此不把它武断归因为新的单一后端故障。当前用真实无扩展名月季图重新验证得到 HTTP 200、植物候选、随图配文自然回复和完整结构化字段；若以后再次失败，页面继续显示后端真实原因，而不是把所有错误折叠成同一条泛化提示。
- 旧流程把“选择图片”和“发送给 Vision”绑在同一个点击处理函数里，导致用户无法在发送前检查、移除或补充文字。这是 M6 新功能交互缺陷，不是旧项目遗留问题。当前重组为“本地附件草稿 -> 用户补充文字/移除 -> 点击发送 -> 首次同意 -> 同一轮 Vision 请求”。
- 初版 M6 页面在重组助手头部时移除了旧本地界面中未接线的输入区“+”，又自行新增了顶部独立 Vision 按钮；这是由本次集成修改造成的前端回归，不是旧项目遗留问题。当前已删除顶部按钮，恢复并接通输入区“+”。
- 长回答把输入区推到屏幕外后，初次修复把页面改成固定视口，却错误地把 `150rpx` 底部留白放在 `scroll-view` 外壳，并在加载占位变成长回答时重复设置同一个消息 id；微信没有按新高度重新滚动，形成“看得见但消息滚不到”的死区。这是本次修改诱发的集成回归。当前保留固定聊天壳和独立输入区，只把内边距移到 `message-list`，并通过清空锚点后定位 `message-end` 强制按新高度重算。
- 随后的紧凑化修复虽然把 `input-panel` 设为透明，却仍让它作为 flex 子项占据整块高度，所以视觉上继续出现长方形底板；这是本次修改诱发的布局回归。当前把它改为固定透明浮层，让消息区延伸到其下方，并用末尾滚动安全区防止最后一条消息被浮层遮挡。
- 新增职责域门禁时，问候正则漏掉了尾部问号，导致 `你好?` 被判为域外，而 `你好` 又会携带先前域外数学历史进入模型；这是本次修改诱发的意图路由回归。当前先归一化无语义尾部标点，简单问候直接返回一致的社交回复，并从后续模型上下文中排除成对的域外原始问答。
- 上一版把 `mentionedPlantCount > 0` 直接视为域内，导致算术、创作等只要夹带“月季/玫瑰”就进入 RAG；同时通用“记住、观察、识别”和宽泛跨轮词也存在误放行。固定的 `applyPlantTopicMismatch` 又无条件在模型答案前拼两段错配模板，使回复突兀且不看用户真实意图。这两点均由本次 M6 意图/错配实现诱发，不是旧项目遗留问题。当前改为植物锚点与领域意图组合，并让现有一次 LLM 调用自然表述真实错配；代码继续拥有所有数据与副作用门禁。
- 对抗测试还发现“给这篇文章浇水”会被宽泛省略句规则误放行；收紧后真实冒烟又发现“给月季浇牛奶”会被误拒绝。两者已经分别作为负例和正例固化，说明本轮不是只围绕两张截图追加特判。
- 二态规则继续收紧后又把“月季是什么”和“我是谁”机械判为域外；这是上一轮 M6 正则加固诱发的集成回归。植物开放表达仍采用 `in_scope / out_of_scope / deferred` 三态策略；账号称呼则从临时 `deferred` 模型回退进一步收敛为资料驱动的确定性分支，避免邀请昵称后下一次又忘记。昵称的唯一事实来源是 `users.nick_name`，不复制到 `ai_memories`。固定语料全部通过仍不等于开放语言百分百准确；后续需要以真实 false accept、false reject 和 defer rate 持续评估。
- 本轮架构审计确认：此前把现有测试集合笼统描述为 Agent/harness 不够准确。当前产品是受控工作流；新增的是评测/验收 harness，不是规划、工具循环、subagent 和 durable execution 的运行时 harness。
- 本轮修复没有新增、改变或关闭本地化妥协；LC-04、LC-05、LC-07 的云迁移边界保持不变。

## 7. 云后端切换时必须迁移或恢复

M6 没有调用服务器已有 Key，也没有修改腾讯云环境。转向云后端时必须一次完成以下事项：

1. 停止读取 `D:\植宠项目\API-key.txt`，由用户按既定决定安全处置本地文件。
2. 云端只从服务器环境变量/密钥管理读取 `LLM_API_ENABLED`、`LLM_API_BASE_URL`、`LLM_API_PATH`、`LLM_API_KEY`、`LLM_MODEL` 和 `VISION_MODEL`；Chat/Vision 在同一云环境统一使用服务器已有那套 Key，不与本地 Key 混用。
3. 服务器当前已确认的 Chat 配置仍以既有 `qwen3.6-flash-2026-04-16` 环境为准；Vision 上线前必须为同一服务端凭证配置并实测一个实际支持图片输入的模型，不能直接沿用本地 DeepSeek 模型名或只改配置后宣称完成。
4. 受控迁移 `ai_assistant.m6.sql` 结构；验证 openid 归属、20 轮/30 天清理、全账户无限策略、Asia/Shanghai 用量记账和 PlantPet 永久删除联动。
5. 把诊断图片从 `local://`/MySQL BLOB provider 切换到团队最终授权的 CloudBase 或 COS 生命周期；上传、解析、替换、删除和跨账号隔离都要在目标云资源实测。
6. 恢复真实 `auth-scf code2Session`、HTTPS 合法域名和独立 Auth/API/Agent 地址；本地聚合服务、固定 openid 和 `/dev/token` 不进入部署。
7. 使用体验版和指定安全测试设备重新执行 Chat、Vision、RAG、记忆、任务确认、无限状态/用量记账与模型失败路径。

对应恢复项见 `docs/localization-compromise-register.md` 的 LC-01、LC-02、LC-03、LC-04、LC-05、LC-06、LC-07 和 LC-08。完成这些恢复前，本地通过不能表述为线上或体验版可用。
