# M6 会话、附件、记忆与检索扩展决策

> 历史/目标文档提示（2026-09-08）：本文保留该阶段的配置、调研或实施记录，不作为当前能力与验收状态清单。旧记忆、额度、rollout 和云端结论如与后续版本不同，以当前入口为准。 当前产品见[先看这里](./先看这里.md)，技术事实见[当前架构](./current-architecture.md)。

> 状态：本地实现与真实开发者工具验证完成，待用户验收  
> 决策日期：2026-08-31  
> 适用范围：微信小程序本地 M6；不代表体验版或线上已更新

## 1. 为什么扩展

当前 M6 已完成单植宠单会话、文本对话、图片草稿与图片分析、结构化记忆展示、published-only 知识检索，以及用户确认后的任务/诊断写入。本轮扩展解决以下已验收发现：

- 输入框“+”只能选择拍照或相册，不能添加文档，也不能显式选择现有产品功能；
- 同一植宠只有一个固定会话，无法把不同主题分开；
- 已发送的文本没有撤回或重新编写入口；
- 记忆页把用户确认偏好、业务来源事实和 AI 摘要平铺成同一种可编辑对象，容易让用户误解来源；
- 当前知识文章检索依赖整句子串命中并把整篇正文加入上下文，短问法、同义表达和长文章的局部命中不稳定。

## 2. 参考模式与取舍

本轮只吸收与植宠 MVP 直接相关的成熟做法，不复制通用 Agent 平台的运行时：

- Open WebUI 把普通对话、附件、文档、记忆和工具作为同一会话上的可选能力；消息编辑使用分支结构保留原路径；知识检索区分整篇注入与按相关片段检索。
- LibreChat 的 Fork 会把选定消息以前的上下文复制到新会话，原会话保持不变；其记忆明确区分会话历史与跨会话结构化记忆，并提供用户可见的增删改和按会话开关。
- 两者都把附件和能力选择保留在 composer 内，用户选中后仍可补充文字，而不是点击后立即执行。

## 3. 本轮产品工作流

### 3.1 “+”菜单

输入框旁“+”只展开两个一级入口：

1. **添加附件**：继续展开“拍照 / 从相册选择 / 选择文档”；
2. **选择功能**：列出当前已经实现且用户有权使用的产品功能。

暂不提供 `@ 添加上下文`、`/ 能力`、`$ 技能`。当前小程序没有跨会话/跨 Agent 上下文，也没有技能运行时；提前展示这些入口会造成虚假能力暗示。

### 3.2 选择功能不是自主 tool calling

“选择功能”是前端确定性 launcher：

- 查看植株状态、浇水建议、读取记忆：在 composer 中形成可移除的功能 chip，并填入可编辑的标准问句；发送后仍走现有 `/agent/chat`；
- 创建养护任务：跳转到现有 `pages/taskForm`，最终写入仍要求用户检查并提交 `confirmed=true`；
- 管理 NOVA 记忆：跳转到 `pages/aiMemory`。

模型不会获得一个可自主循环调用的工具目录，也不能跳过确认表单创建任务、修改植宠、控制设备或写用户资料。

### 3.3 文档附件

文档与图片一样先进入草稿，用户可继续填写问题、移除附件，点击发送后才处理。当前本地 MVP 支持：

- 纯文本：TXT、Markdown、CSV、JSON；
- 常用办公文档：PDF、DOCX；
- 单个文件，最大 1 MB；旧 `.doc`、扫描件 OCR、表格计算和压缩包不在本轮能力内。

原文件以 `conversation_document` 保存到当前 JWT 账号的本地媒体 provider，并在成功生成该轮消息后关联 `ai_message`。提取出的文本只用于当前模型请求和该轮可读摘要，不作为长期记忆。文档内容被标记为不可信参考资料，不能覆盖 NOVA 角色、权限或系统指令。

云端迁移时必须把 `conversation_document` 与现有 `conversation_image` 一起迁移到获批的云媒体 provider；本地 MySQL BLOB 仍只是开发期替代。

### 3.4 同一植宠多会话

- 每个植宠可拥有多个 `ai_conversations`；
- 页面提供当前会话切换和“新对话”；
- 首条用户文本为“新对话”生成短标题；
- 植宠切换只展示该植宠自己的会话；账号归属仍由 JWT openid 决定。

欢迎卡不是数据库消息。新建空会话不会复制旧会话记忆或附件；跨会话只读取结构化、可治理的植宠事实/偏好，不搜索全部历史聊天。

### 3.5 重新编写与撤回

- **入口**：消息默认态不显示操作控件。长按本人用户消息后，在气泡附近显示临时的图标加文字菜单；纯文字消息和已保存原件的图片/文档消息提供复制和重新编辑，只有当前最后一轮额外提供撤回本轮。重新编辑附件消息时，原文字与原附件先回填 composer，发送后创建新分支且保留原会话；历史上没有保存原件的旧附件消息不显示无法兑现的重新编辑入口。该模式以用户提供的 ChatGPT、DeepSeek、腾讯元宝三组手机实景“默认态 / 长按态”为视觉主基准，并沿用现有 Open WebUI/LibreChat 源码中的能力门禁思想。菜单使用覆盖层，不增加每条消息高度；点空白、滚动、切换页面或执行动作后关闭。
- **重新编写**：只对用户文本消息提供。提交新文本时，后端把目标消息之前的直接历史复制到一个新会话，再在新会话发起新的一轮回答；原会话及其证据保持不变。
- **撤回本轮**：只对当前会话最后一条用户消息提供，删除该用户消息、紧随其后的回答以及该轮 `ai_message` 附件。限制在最后一轮是为了不暗中删除或改写后续上下文。
- 图片或文档消息本轮可撤回；其附件随该轮删除。包含附件的旧消息暂不支持“重新编写并复用原附件”，用户可新建会话并重新添加附件。

这不是通用消息树或全量版本控制；MVP 使用“复制前缀到新会话”的可解释分支方式。

## 4. 记忆策略

记忆分成三个用户可理解的来源层：

| 层 | 内容 | 用户操作 | 模型权限 |
| --- | --- | --- | --- |
| 用户明确让我记住 | `user_preference` | 新增、修正、删除 | 只有用户明确保存或明确要求记住时才可进入 |
| 植宠事实与养护记录 | `plant_fact`、`business_event` | 查看、去来源修改、遗忘派生副本 | 来自档案/任务/日记/诊断，只读派生；源仍是业务表 |
| 旧版 NOVA 对话摘要 | `ai_summary` | 查看、删除 | 停止新写入，也不再注入模型上下文 |

会话历史继续承担单会话上下文；结构化记忆只承担跨会话的稳定事实和显式偏好。普通回答不再自动保存为长期 `ai_summary`，避免模型回答反复喂回模型。

## 5. RAG 策略

当前只有 10 篇经人工审核发布的文章和 17 条植物档案，不引入向量库。检索继续以 MySQL published 内容为唯一主源，JSON 只在数据库请求失败时 fallback。

本轮采用轻量确定性检索：

1. 中文/英文归一化和领域词切分；
2. 标题、别名、标签、植物类型、问题类型、摘要、正文按不同权重计分；
3. 长正文按段落切分，只把最相关片段加入模型上下文；
4. 同一文章只返回一个来源卡，片段去重；
5. 没有足够字段/词项证据时保持 unknown，排序权重不能把无关文章变成命中；
6. 用黄金/对抗语料验证短问法、同义表达、植物名与问题混合、无关词夹带和无答案场景。

这仍是 retrieval pipeline，不是模型自主浏览知识库，也没有新增第二次分类模型调用。

## 6. 架构边界

- **产品工作流**：composer 选择 -> 用户补充 -> 单次请求 -> 只读建议或用户确认页面；
- **Agent framework**：没有引入 LangChain、LangGraph 或其他通用框架；
- **Agent runtime**：仍是确定性职责路由 + 至多一次 Chat/Vision 调用；
- **运行时 harness**：没有；
- **评测 harness**：现有本地 smoke、意图语料和微信开发者工具自动化，新增会话/附件/检索用例；
- **工具与副作用权限**：模型没有自主工具调用；任务、诊断、偏好仍由用户显式确认；
- **未实现**：多 Agent、handoff、subagent、后台执行、checkpoint、跨会话历史语义搜索、向量数据库、OCR、文档编辑或自动上传知识库。

## 7. 验收重点

- 加号菜单紧凑且不遮住历史；选附件/功能后仍可输入；
- 图片原流程不回退；文档只在发送时处理且切页后仍能看到附件元信息；
- 同一植宠可新建并切换至少两个互不串话的会话；
- 重写产生新会话且原会话不变；撤回只作用于最后一轮并清理附件；
- 普通图片建议不产生任务；只有明确创建/安排/提醒意图才出现任务候选；
- 派生事实不可被当作用户偏好直接编辑；旧 AI 摘要不再进入模型上下文；
- RAG 对“月季怎么浇”“龟背竹黄叶”等短问法命中正确来源，对数学/无关内容保持无来源；
- 账号 A 不能列出、切换、重写、撤回、解析账号 B 的会话、消息或附件；
- 从登录页开始的微信开发者工具真实流程无页面异常。

## 8. 文档级与代码级重审结论

本轮在调研后重新从当前工作树核对，而不是把成熟产品做法直接套到旧认知上：

| 检查面 | 当前实现证据 | 结论 |
| --- | --- | --- |
| PRD 主流程 | 四 Tab、PlantPet、日历任务、个人资料和知识页仍在；M6 只扩展助手及记忆子页 | 没有把项目改造成通用 Agent 平台 |
| 身份与归属 | 新会话、分支、撤回、文档解析都从 JWT openid 校验会话和 PlantPet owner | 没有新增客户端 openid 回退 |
| Composer | `pages/assistant` 的两级“+”菜单、附件草稿、功能 chip 与浮动布局 | 顶部独立拍照入口不再恢复；功能选择不会立即执行 |
| 会话模型 | `agent-store.js` 的 list/create/fork/withdraw 与既有 20 轮/30 天清理 | 多会话和分支复用原表，不引入消息树框架 |
| 文档 | `documentHandler.js`、`conversation_document` 媒体用途、PDF/DOCX 提取依赖 | 文档只作本轮不可信资料，不写长期记忆或知识库 |
| 记忆 | `aiMemory` 来源分区；`chatHandler` 停止新写入和召回 `ai_summary` | 用户偏好可治理，业务事实回到原记录，旧摘要逐步退出 |
| RAG | `knowledgeSearch.js` 的字段加权、中文词片、段落选择与 published-only 门禁 | 当前小语料无需向量库，仍保留无证据即 unknown |
| 副作用 | 功能 id 服务端白名单；任务走现有确认表单；文档/普通图片不产任务 | 模型没有工具循环或业务写权限 |
| 测试 | 单元/集成、真实本地 smoke、微信开发者工具完整路径 | 不以直接注入页面状态替代真实操作 |

重审同时确认一个需要长期保持的边界：当前所谓“选择功能”是产品 launcher 和请求上下文标记，不是 OpenAI/LangChain 风格的运行时 tool calling。模型不能动态枚举、选择或循环调用工具。以后若要引入真实工具调用、跨会话上下文、跨 Agent、后台运行或 checkpoint，必须作为新的上层架构变更单独披露和确认。
