# 设备字段协议草案

> 更新日期：2026-05-14

## 1. 目标

定义当前项目中设备上报字段的统一解释，用于：

- 前端展示
- Agent 理解与问答
- 后端字段映射
- RAG 字段协议知识库

原则：

- 硬件端为状态来源
- `device_latest.params_json` 为当前事实快照
- 字段解释必须统一，避免不同层各自猜测

## 2. 通用数据结构

建议 latest 中统一使用如下结构：

```json
{
  "soil_percent": {
    "value": 18,
    "time": 1747213200000
  }
}
```

字段说明：

- `value`
  - 实际值
- `time`
  - 该值对应的采样或上报时间戳

兼容说明：

- 当前系统对部分布尔字段也兼容直接布尔值
- 但推荐统一为 `{ value, time }`

## 3. 当前已使用字段

### 3.1 `soil_percent`

含义：

- 土壤湿度百分比

类型：

- `number`

单位：

- `%`

典型用途：

- 判断是否缺水
- 生成浇水建议
- 绘制湿度趋势

前端消费位置：

- 首页
- 设备详情页
- Agent 诊断

### 3.2 `dht_temp`

含义：

- 环境温度

类型：

- `number`

单位：

- `℃`

典型用途：

- 判断环境温度是否异常
- 决定是否建议通风

### 3.3 `dht_humi`

含义：

- 环境湿度

类型：

- `number`

单位：

- `%`

典型用途：

- 判断环境过干或过湿

### 3.4 `light_val`

含义：

- 光照强度

类型：

- `number`

单位：

- `lx`

典型用途：

- 判断光照不足或过强

### 3.5 `dsb_temp`

含义：

- 探针温度

类型：

- `number`

单位：

- `℃`

典型用途：

- 辅助诊断局部温度状态

说明：

- 当前前端有展示，但未做主要风险判断

### 3.6 `run_state`

含义：

- 设备运行状态

类型：

- `boolean`

推荐解释：

- `true`：运行中
- `false`：已停止

典型用途：

- 给用户展示设备当前状态

### 3.7 `ir_status`

含义：

- 红外状态

类型：

- `boolean`

推荐解释：

- `true`：触发
- `false`：正常

典型用途：

- 展示附加状态
- 后续可作为事件判断依据

### 3.8 `uid`

含义：

- 设备端上报的唯一标识或模块标识

类型：

- `string` 或 `number`

典型用途：

- 调试展示
- 排障辅助

### 3.9 `test`

含义：

- 当前风扇开关的临时物模型标识符

类型：

- `boolean`

推荐解释：

- `true`：风扇开启
- `false`：风扇关闭

说明：

- 当前为历史过渡字段
- 后续建议统一切换到 `fan_switch`

### 3.10 `fan_switch`

含义：

- 风扇开关状态的正式字段名

类型：

- `boolean`

推荐解释：

- `true`：风扇开启
- `false`：风扇关闭

说明：

- 当前前端和后端应兼容 `fan_switch` 与 `test`

## 4. 当前前端映射

首页和详情页当前映射关系建议保持如下：

- 温度：`dht_temp` -> `temp`
- 湿度：`dht_humi` -> `humidity`
- 光照：`light_val` -> `light`
- 土壤：`soil_percent` -> `soil`
- 风扇状态：`fan_switch || test`

若后续硬件端字段名有变化，应优先更新字段协议，再同步修改前端映射。

## 5. Agent 建议消费方式

Agent 不建议直接面向原始字段名做自由推理，建议先做一层结构化映射：

```json
{
  "temperature": 29,
  "humidity": 51,
  "soilMoisture": 18,
  "lightLux": 1380,
  "fanState": false,
  "deviceRunning": true
}
```

这样做的好处：

- 降低 prompt 中的硬件细节噪音
- 提高模型解释稳定性
- 便于后续字段演进

## 6. 推荐扩展字段

如果硬件端后续已经计算出更高阶状态，建议优先采用“直接上报结果字段”的方式，而不是让云端重复计算。

建议预留以下字段：

### 6.1 `mood_level`

含义：

- 植物当前情绪等级

类型：

- `string`

建议取值：

- `good`
- `neutral`
- `bad`

### 6.2 `emotion_code`

含义：

- 表情或状态表现编码

类型：

- `string`

用途：

- 前端切换表情资源
- Agent 更自然地解释当前状态

### 6.3 `affinity_score`

含义：

- 好感度或综合状态分数

类型：

- `number`

建议范围：

- `0 ~ 100`

### 6.4 `life_state`

含义：

- 生命周期状态

类型：

- `string`

建议取值：

- `healthy`
- `warning`
- `critical`
- `recovering`

### 6.5 `need_water`

含义：

- 是否需要浇水

类型：

- `boolean`

用途：

- 降低 Agent 推理成本
- 直接驱动待办与提醒

### 6.6 `need_ventilation`

含义：

- 是否建议通风

类型：

- `boolean`

### 6.7 `display_mode`

含义：

- 设备端建议的显示模式

类型：

- `string`

用途：

- 驱动屏幕端和前端的一致表现

## 7. 字段协议维护建议

每新增一个设备字段，都建议记录以下信息：

- 字段名
- 中文含义
- 数据类型
- 单位
- 是否为硬件计算结果
- 前端是否直接展示
- Agent 是否可直接解释
- 是否参与风险判断

建议后续将该文档同步抽成：

- 前端映射配置
- Agent 字段知识文档
- 后端字段校验表
