# TRT Nova 植宠系统实施顺序与演进路线

> 文档定位：从当前 SCF Demo 演进到产品级植宠系统的唯一实施顺序  
> 输入依据：[当前系统现状与改进路线](./current-system-status-and-improvement-plan.md)、[产品技术栈定版](./plant-pet-technical-architecture-brief.md)  
> 使用原则：保持每一步都可部署、可演示、可回滚；未达到退出条件，不进入下一步  
> 基线日期：2026-07-18  
> 最近审阅：2026-07-19

## 1. 总体策略

当前 SCF 架构不是需要丢弃的临时代码，而是后续产品化的起点。近期继续维持以下部署单元：

| 当前部署 | 近期承载职责 |
|---|---|
| `auth-scf` | 微信登录、Token 和身份边界 |
| `api-scf` | 用户、植宠、绑定、养护、任务、动作和时间线 |
| `ingest-scf` | OneNET webhook、遥测归一化、latest/raw/aggregate |
| `agent-scf` | 对话、知识和受控工具编排 |
| `history-cleanup-scf` | 遥测保留和清理 |
| MySQL | 当前业务事实、设备状态和有限周期遥测 |

目标架构中的“身份、植宠、养护、数字孪生、动作、记忆”等首先是**代码模块**，不等于马上创建独立服务。实施步骤使用 `R0—R10` 标记，与技术架构中的研发阶段 `T0—T3`、容量等级 `S0—S3` 分开。R0—R6 原则上仍使用上述 SCF；只有第 10 节指标触发后才增加部署单元或基础设施。

实施过程固定采用以下循环：

> 先锁定当前行为 → 增加测试 → 做兼容性变更 → staging 验证 → 小流量发布 → 观察 → 扩大流量 → 保留回滚

## 2. 一页实施总览

| 顺序 | 实施步骤 | 得到的可见成果 | 是否新增云组件 |
|---:|---|---|---|
| R0 | 冻结当前基线 | Demo 有唯一版本且随时可回退 | 否 |
| R1 | 安全与发布基线 | Demo 可供真实用户安全试用 | 仅 staging/密钥与告警 |
| R2 | 工程框架渐进迁移 | 多人可在统一 TypeScript 工程协作 | 否 |
| R3 | 设备链路可靠化 | 上报、查询、控制状态可信 | 否 |
| R4 | 独立 PlantPet 模型 | 植宠不再等同于设备 | 否 |
| R5 | 养护行动闭环 | 建议能转化为任务/行动并验证结果 | 否 |
| R6 | Agent 产品化 | Agent 有事实来源、评估和安全工具调用 | 否 |
| R7 | 内测运营闭环 | 可告警、可恢复、可支持连续真实试用 | COS 按媒体需要启用 |
| R8 | 陪伴能力深化 | 人格、关系、记忆和主动互动稳定 | 视实时负载容器化 |
| R9 | 社区与多端 | 社区、后台和 Flutter 按产品证据上线 | COS/CDN，搜索按门槛 |
| R10 | 规模化 | 数据与运行平台按指标扩展 | Redis/CKafka/TCHouse-C/ES/TKE 按需 |

参考节奏以 2—4 人软件团队计算，R0—R3 通常需要 4—8 周，R4—R7 通常需要 8—16 周。时间只用于排期参考，退出条件比日期优先。

## 3. R0：冻结当前 Demo 基线

**目的**：在改造前得到一个不会丢失的可运行起点。

按顺序执行：

1. 选定唯一正式目录、分支和数据库 Schema；兄弟目录只作为迁移来源，不同时继续开发。
2. 清点线上 4 个业务 SCF、清理任务、域名、触发器、环境变量、OneNET 配置和数据库版本。
3. 从登录、绑定、设备上报、latest 查询、风扇控制到 Agent 问答，录制一次完整验收结果。
4. 为当前可部署版本打标签，保存部署 manifest、数据库备份和回滚说明。
5. 建立“现状问题不阻塞基线冻结”的原则：先记录缺陷，不在盘点过程中顺手重构。

**退出条件**：任何成员都能从同一 commit 找到部署包、配置说明和数据库版本，并能恢复当前 Demo。

## 4. R1：安全与可重复发布

**目的**：让 Demo 从“能展示”变成“可让真实用户试用”。

按顺序执行：

1. 轮换数据库、微信、JWT、OneNET 和模型凭证；示例文件只保留占位符。
2. 删除 openid 和本地手机号身份回退；所有身份验证 fail-closed。
3. 设备控制只开放 `fan_on`、`fan_off` 等业务动作，禁止普通用户提交任意物模型 JSON。
4. 增加 owner/ACL、动作白名单、频率限制、幂等键和控制审计。
5. 建立 staging，与 production 隔离数据库、凭证、域名和 OneNET 测试设备。
6. 统一 SCF 运行时、依赖版本和 lockfile；由 CI 构建部署包，不在源码中维护 `node_modules`。
7. 建立最小流水线：安装、检查、测试、构建、部署 staging、冒烟测试、人工批准生产。

**退出条件**：伪造身份和越权控制测试失败；staging 可从干净环境重复部署；生产制品能追溯到唯一 commit 并可回滚。

## 5. R2：工程框架渐进迁移

**目的**：建立长期代码框架，但不暂停现有功能开发，也不一次性重写全部 SCF。

目标仓库先形成：

~~~text
apps/
  mini-program/
  auth-scf/
  api-scf/
  ingest-scf/
  agent-scf/
  cleanup-scf/
packages/
  contracts-api/
  contracts-device/
  domain-identity/
  domain-device/
  observability/
  test-fixtures/
infrastructure/
docs/
~~~

迁移顺序：

1. 建立 pnpm workspaces、TypeScript strict、ESLint、Vitest 和统一构建脚本。
2. 先把请求、响应、设备 payload、环境变量写成 Zod 契约，不改变接口行为。
3. 为现有登录、绑定、上报、latest、控制和 Agent API 建立特征测试。
4. 将公共数据库连接、鉴权、错误、日志和 traceId 提取到明确包中。
5. `api-scf` 新增业务使用 NestJS + Fastify + Drizzle；先迁移一个只读纵向切片，再迁移写接口。
6. `auth-scf`、`ingest-scf` 和 `agent-scf` 逐个迁移到 TypeScript；简单触发器可以保留轻量 TypeScript handler，不为形式强制启动完整 Nest 应用。
7. 每迁移一个入口，保持 URL、请求和响应兼容，staging 对比新旧结果后再切换。

**退出条件**：新成员可用一条安装命令启动开发；核心接口有类型和契约；任一 SCF 可从源码重复构建；迁移期间 Demo 功能没有整体停摆。

## 6. R3：设备链路可靠化

**目的**：先把植宠赖以判断的设备事实做可信，再增加更多智能功能。

按数据流实施：

1. 定版设备身份：`productId + deviceName = logicalKey`，数据库内部增加稳定 `device_id`。
2. 定版遥测契约：字段名、类型、单位、采样时间、接收时间、质量状态和协议版本。
3. `ingest-scf` 增加 event_id/业务唯一键、重复消息幂等、异常消息隔离和失败可重放记录。
4. latest 保存最后有效值、采样时间和新鲜度；读取失败时展示上次数据并明确标记陈旧，不伪造离线或零值。
5. raw/aggregate 建立明确保留期、聚合口径和清理结果指标。
6. 命令建立 `requested → approved → dispatched → acknowledged → verified/failed/timed_out` 状态机。
7. 将命令回执和后续属性变化关联，区分“平台已接收”和“设备已执行”。
8. 建立登录—绑定—上报—latest—控制—回执自动 E2E，并覆盖重复、乱序、弱网和 OneNET 故障。

**退出条件**：设备状态有来源、时间和新鲜度；重复上报不产生重复事实；控制全过程可审计；外部故障不会向用户显示虚假成功。

## 7. R4：建立独立 PlantPet 领域

**目的**：从“设备上挂了一棵植物”升级为“植宠可以关联和更换设备”。

数据库迁移固定使用扩展—迁移—切换—清理流程：

1. 新增 `plant_pets`、`pet_device_bindings` 及必要版本字段，不删除旧列。
2. 编写可重复、可校验、可回滚的 backfill，为现有绑定生成 PlantPet。
3. API 同时兼容旧设备视角和新 PlantPet 视角，新客户端优先使用 `plantPetId`。
4. todo、日记、Agent 会话和养护结果逐步从 `device_id` 迁移到 `plant_pet_id`。
5. 增加换设备、换植物、解绑、历史时间范围和多人协作测试。
6. 观察一个完整版本周期后，再停止旧字段写入；删除旧结构必须单独评审。

**退出条件**：植宠换设备后保留身份、成长、日记和记忆；设备换植物后历史不会串到新植宠；旧客户端在迁移窗口仍可使用。

## 8. R5：打通养护行动闭环

**目的**：让系统不只展示数据或聊天，而是真正帮助用户完成养护。

只实现一条最小但完整的纵向链路，再扩展其他场景：

> 土壤偏干 → Assessment → Recommendation → CareTask/ProposedAction → 用户确认 → CareAction → 设备或人工反馈 → 效果复查 → TimelineEvent

实施顺序：

1. 服务端建立版本化植物阈值和规则，客户端只展示结果。
2. 建立 Assessment、Recommendation、CareTask、CareAction、TimelineEvent 数据模型。
3. 建议可以生成任务；设备动作必须经过用户确认和 R3 的动作状态机。
4. 支持用户记录人工浇水、施肥、修剪等行为。
5. 在预定时间或新遥测到达后复查效果，形成恢复、未改善或未知结果。
6. 先完成土壤干燥场景，再复制到温度、光照、湿度和离线场景。

**退出条件**：任一养护结论能追溯到设备事实和规则版本；建议、任务、行动、结果和时间线形成闭环；失败可以恢复且不会重复执行。

## 9. R6—R9：从可用产品到完整产品

### R6：Agent 产品化

- Agent 只通过 Tool API 获取设备、PlantPet、规则和任务事实，不直连数据库或 OneNET；
- 回答展示数据时间和来源，无数据时明确表达未知；
- 建立黄金评估集，覆盖事实、建议、人设、安全、拒答和故障降级；
- 设备动作先生成 ProposedAction，由业务后端重新校验权限、状态和有效期；
- 在线编排保持 TypeScript，Python 只做知识处理和离线评估。

**退出条件**：Agent 错误不会影响基础设备功能；事实正确率、建议有用率和工具成功率达到预设目标。

### R7：内测运营闭环

- 增加通知、关键指标、Dashboard、告警、备份恢复演练和 Runbook；
- 建立最小运营后台，支持设备诊断、用户查询、植物内容和功能开关；
- 开展至少四周连续真实试用，记录留存、任务完成、建议采纳、故障和单位成本。

**退出条件**：核心故障能在用户投诉前发现；支持人员无需直接改生产数据库；四周数据足以决定后续投入。

### R8：陪伴能力深化

- 建立 Persona、RelationshipBond、EmotionState、长期记忆和成长里程碑；
- 软件和硬件共享人格版本、会话摘要和受控记忆；
- 使用流式 WSS WebSocket 实现实时互动，达到长连接门槛后只迁移 interaction 到容器；
- 以人设一致性、回应延迟、用户回访和安全评估作为退出标准。

### R9：社区与多端

- 先做私人内容显式发布、媒体上传、审核、举报和删除，再做 Feed、互动和推荐；
- 管理后台先覆盖客服、设备和审核，不先建设复杂数据平台；
- Flutter 只有在 App 独有的硬件、实时互动或分发需求成立后正式投入；
- 社区与 App 分别立项，不与养护核心绑成一次大版本。

## 10. 什么时候才增加基础设施

| 新能力 | 不增加时怎么做 | 触发后怎么做 |
|---|---|---|
| Redis | MySQL 唯一约束、短期本地缓存 | 出现多实例共享缓存、限流、会话或短锁后启用 |
| CKafka | MySQL Outbox + worker | Outbox 积压影响事务库，或需要消费组、设备保序和长时间重放后启用 |
| TCHouse-C | MySQL raw + aggregate + 保留清理 | MySQL 无法满足遥测写入、历史查询或单位存储成本后迁移遥测历史 |
| Elasticsearch | MySQL 索引和简单知识检索 | 社区/知识需要全文、混合或向量检索且 MySQL 无法达标后启用 |
| 容器 | SCF | 出现常驻 CPU、长连接、执行限制，或 SCF 综合成本明显更高时迁移对应服务 |
| TKE Serverless | 少量独立容器 | 达到约 8—10 个常驻工作负载且有平台 owner 和值班能力后启用 |

升级只迁移受到瓶颈影响的部分。例如 interaction 转容器后，webhook、清理和低频任务仍可继续使用 SCF。目标不是消灭 SCF，而是让每类负载运行在合适的位置。

## 11. 团队如何并行而不互相阻塞

| 轨道 | 可以开始的时间 | 主要工作 |
|---|---|---|
| A：安全与工程 | 立即 | R0—R2、契约、CI、环境和发布 |
| B：IoT 与数据 | 契约初稿完成后 | R3、设备模型、遥测和命令状态机 |
| C：植宠与养护 | Schema/migration 基线完成后 | R4—R5、规则、任务和时间线 |
| D：小程序体验 | API 契约稳定后 | 状态语义、植宠视角、任务和结果展示 |
| E：Agent | 设备事实和 PlantPet API 稳定后 | R6，不提前直接操作设备 |
| F：运营/社区/App | 核心闭环真实试用后 | R7—R9 |

如果只有一名主要开发者，严格按 R0→R1→R2→R3→R4→R5→R6→R7 推进；如果有多人，允许相邻轨道并行，但数据库 Schema、API 契约和设备协议必须先合并再开发消费者。

## 12. 每个步骤统一完成标准

一个步骤只有同时满足以下条件才算完成：

1. 功能在 staging 和目标终端通过；
2. 关键成功与失败路径有自动化测试；
3. 数据 migration 可前滚、可校验，破坏性清理延后执行；
4. 日志脱敏，指标和告警能够发现主要故障；
5. 部署制品对应唯一 commit，具备回滚步骤；
6. API、Schema、运行手册和现状文档同步更新；
7. 没有把后续步骤的基础设施偷偷变成当前步骤的前置条件。

## 13. 现在就开始的第一批任务

建议第一个迭代只安排以下事项：

1. 确认唯一主线并给当前可运行 Demo 打标签；
2. 轮换和清理凭证，关闭身份回退与任意命令入口；
3. 列出生产/staging 的 SCF、域名、触发器、Schema 和环境变量；
4. 统一 Node 运行时、依赖版本和 lockfile，停止维护提交进仓库的 `node_modules`；
5. 为登录、绑定、上报、latest 和风扇控制补最小冒烟/E2E；
6. 建立 staging 和最小 CI 部署；
7. 评审通过后再开始 TypeScript/契约渐进迁移。

第一批任务完成前，不启动 Redis、CKafka、TCHouse-C、Elasticsearch、TKE、Flutter 正式 App、社区或 Agent 自动控制。
